## Requirement understanding

One line: Add a new tool to the IT Glue MCP connector that adds a field to an existing flexible asset type (`POST /flexible_asset_types/{id}/relationships/flexible_asset_fields`), so the Rewst flow that today calls `it_glue.create_flexible_asset_field` (EMD Networking Services' "ITG: Upsert Flexible Asset Type" flow) can be rebuilt as an MSPbots agent.

This ticket is item 64 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It targets the Rewst account EMD Networking Services, whose "ITG: Upsert Flexible Asset Type" flow (an unexecuted branch in the last ~365 days, evidence level C) calls IT Glue's `it_glue.create_flexible_asset_field` action to add a new custom field (e.g. a Tag field) to an existing flexible asset type. The gap register's own example payload is `{"data":{"attributes":{"kind":"Tag","name":"Full Access Record","order":"860","tag_type":"Contacts","show_in_list":false}}}`. The ticket separately notes the IT Glue connector is "Not Connected" on the mspbots tenant and that an earlier observation of a first-version tenant's connector found only `list_flexible_asset_types` / `search_flexible_assets` among 33 tools, with no create/update/read-by-id and no contacts support — that observation is about a vendor connection/registration state and an older deployment, not about this repository; it is not evidence of this repo's current code (see Current state below, which is read directly from the repo).

## Product design

### Goals / Non-goals

**Goals**

- Add one new write tool, `itglue_create_flexible_asset_field`, that adds a field (custom schema entry) to an existing IT Glue flexible asset type, matching the capability the ticket asks for and the Rewst flow it replaces.
- Accept the same attributes IT Glue's create-field endpoint takes (`name`, `kind` required; `order`, `required`, `show_in_list`, `use_for_title`, `tag_type`, `hint`, `default_value` optional), forwarding only what the caller sets — same "only send what's passed" convention every other create/update tool in this connector already follows.

**Non-goals**

- No tool to update, bulk-update, or delete flexible asset fields — the ticket and the one Rewst flow it names only call create; IT Glue's update/bulk_update/destroy field operations are not requested here and are not built speculatively (YAGNI).
- No change to any existing tool's name, parameters, or behaviour.
- No UI change — this is a connector-level (MCP) change, not an Agent Platform page.
- No new connector and no gateway change — the repo already exists and this is an in-repo addition.
- No change to the vendor connection/registration state the ticket mentions ("Not Connected" on the mspbots tenant) — that is an INT/tenant configuration concern, not a code gap, and is unaffected by adding a tool (per `references/mcp-track.md` §3, a missing/unregistered test account/tenant does not block design or development).

### Acceptance criteria AC1..ACn

- **AC1** — Given a valid `flexible_asset_type_id`, `name` and `kind` (and any of the optional attributes), when `itglue_create_flexible_asset_field` is called, then a new field is created on that flexible asset type and the tool returns the connector's standard single-item envelope containing at least the new field's `id`, matching the shape every other create tool returns.
- **AC2** — Given only the required `name` and `kind`, when `itglue_create_flexible_asset_field` is called, then none of the optional attributes (`order`, `required`, `show_in_list`, `use_for_title`, `tag_type`, `hint`, `default_value`) are sent in the request body — only fields the caller actually passed are included, same as `create_flexible_asset` and every update tool in this connector.
- **AC3** — Given `kind="Tag"` and `tag_type="Contacts"` (the gap register's own example payload) or any other string value for `kind`/`tag_type`, when `itglue_create_flexible_asset_field` is called, then both are forwarded to IT Glue unchanged — the tool does not validate `kind` or `tag_type` locally (IT Glue is the source of truth for which kinds/tag types are legal, same policy this connector already applies to `sort` and other enum-like values).
- **AC4** — Given an invalid or non-existent `flexible_asset_type_id`, when `itglue_create_flexible_asset_field` is called, then it returns the standard `not_found` (or `invalid_argument` for a non-numeric ID) error envelope, never an unhandled exception.
- **AC5** — Given missing or invalid IT Glue credentials, when `itglue_create_flexible_asset_field` is called, then it returns the same structured error envelope as every other tool (`not_configured` when the header is absent, `invalid_argument` when the region/base URL header is malformed).
- **AC6** — Given IT Glue returns a retryable error (429 or 5xx), when `itglue_create_flexible_asset_field` is called, then it is retried with backoff exactly as every other tool; given a non-retryable error (401/403/404/422), it returns the corresponding mapped error without retrying.
- **AC7** — Given the MCP's `tools/list` is queried, when `itglue_create_flexible_asset_field` is registered, then it has `readOnlyHint: false` (it writes), `destructiveHint: false` (it adds, it does not remove or overwrite existing data), no `agent_id` parameter, is listed in `README.md`'s Tools table, and no existing tool loses or changes a name or parameter.

### Open questions

- **Whether the request body needs an explicit JSON:API `"type"` key — not blocking, proceeding on repo convention.** The gap register's own example payload (`{"data":{"attributes":{...}}}`) omits `"type"`, and the public IT Glue developer docs page did not yield a definitive answer for this specific create-field endpoint (checked 2026-10-31; the page lists the resource and its operations but the reachable content does not include this endpoint's full request/response spec). Every comparable relationship-create tool already in this connector (`create_location`, `create_document`, `create_flexible_asset`) sends a `"type"` key via the shared `api.attributes()` helper and all three work against the live API today, so this design follows the same convention (`api.attributes("flexible_asset_fields", values)`) rather than inventing a one-off body shape for this tool alone. If IT Glue's real endpoint rejects an unexpected `"type"` key, that is a `422`-mapped `invalid_argument` response the tool already surfaces structurally (AC4/AC6) rather than a crash — the cost of being wrong here is a clear, retryable-diagnosable error at first real use, not silent corruption. This is the same class of "no live account to verify against" limitation every tool in this connector has had (see Risks).
- **The authoritative `kind` enum is not pinned down.** Neither the ticket nor the reachable public docs give the full list of legal `kind` values (the one example is `"Tag"`). Per AC3 and repo convention, the tool does not validate this locally — IT Glue validates it server-side, same as every other enum-like parameter in this connector (e.g. `sort` values are never locally validated either). Not blocking.
- **No live IT Glue test account is available to DEV01.** Per `references/mcp-track.md` §3 ("completion standard"), missing a vendor test account does not block design or development; the one test case that would most benefit from one is marked accordingly below. The ticket's own note that IT Glue is "Not Connected" on the mspbots tenant is consistent with this and is not a blocker either (tenant connection/registration is independent of whether the tool exists in code).

## Tech design

### Conclusion

Add one new write tool, `itglue_create_flexible_asset_field`, to the existing module `src/itglue_mcp/tools/flexible_assets.py` (no new module, no `server.py` change — that module is already imported and registered). It is a thin JSON:API relationship-create wrapper around `POST /flexible_asset_types/{id}/relationships/flexible_asset_fields`, built entirely from helpers every other create tool in this connector already uses (`api.attributes`, `api.item`, `seg`, `run`). No architectural change, no new dependency, no change to any existing tool.

### Where the current implementation lives

- `src/itglue_mcp/tools/flexible_assets.py:29-150` — the module this tool is added to; `create_flexible_asset` (`:110-124`) and `update_flexible_asset` (`:137-150`) are the closest existing patterns for request-body shape and secret-masking of trait-like free-form values.
- `src/itglue_mcp/tools/locations.py:96-113` and `src/itglue_mcp/tools/documents.py:220-236` — the two existing examples of a relationship-create (`POST /<parent>/{id}/relationships/<child>`), the same URL shape this new tool uses.

- `src/itglue_mcp/api.py:150,163-181,233-239` — `ITGlueClient.post`, `item()`/`flatten()`, `attributes()`.
- `src/itglue_mcp/server.py:19,59` — confirms `flexible_assets` is already registered; no change needed here.
- `README.md:107` — the "Flexible assets" row in the Tools table.
- `tests/fixtures/tools_baseline.json`, `tests/test_tools.py:15-24` — backward-compatibility contract test.
- `tests/test_middleware.py:54,68` — hardcoded live tool count (37 → 38).
- `tests/test_flexible_assets.py` — existing test file for this module; new tests are added here, following `test_create_flexible_asset_happy_path` (`tests/test_flexible_assets.py:48-66`) as the closest pattern.

### Option analysis

- **Chosen — add to the existing `tools/flexible_assets.py` module.** `flexible_asset_fields` is the schema of a `flexible_asset_type` (the type a flexible asset is an instance of); grouping it with the type/asset tools already in this file matches the repo's own "one module per area" convention (`README.md:172`, `AGENTS.md:18`) and needs no `server.py` change.
- **Rejected — a new `tools/flexible_asset_fields.py` module.** Would mirror PRD-21586's "new area, new module" pattern, but flexible asset fields are not a standalone resource area the way Users or Activity are — they only exist in the context of a flexible asset type, and IT Glue's own docs group them under "Flexible Asset Types." Splitting them into a separate file would scatter one logical area across two modules for no benefit.
- **Rejected — fold field creation into `create_flexible_asset`'s existing parameters.** `create_flexible_asset` creates an asset *record* (an instance), not a field on the *type* (the schema). Conflating them would require a confusing dual-purpose signature and would violate the connector's existing one-tool-one-operation shape.

### Reuse & cleanup

- **Reuses:** `api.ITGlueClient.post`, `api.item`/`api.attributes`, `tools/_common.py`'s `CREATE`, `seg()`, `run()`. No new third-party dependency.
- **New tool signature:** `itglue_create_flexible_asset_field(flexible_asset_type_id: int, name: str, kind: str, order: int | None = None, required: bool | None = None, show_in_list: bool | None = None, use_for_title: bool | None = None, tag_type: str | None = None, hint: str | None = None, default_value: str | None = None) -> str`. `flexible_asset_type_id`, `name` and `kind` are the only required parameters (matching the ticket's `id*`/`name*`/`kind*`); everything else is optional keyword, same shape discipline as `create_location`/`create_flexible_asset`, so future optional attributes IT Glue adds can be appended without breaking existing callers.
- **Decision — mask `default_value` and `hint` the same way `traits` are masked, not more.** `flexible_assets.py:22-24`'s `_trait_secrets()` treats any string trait value as potentially sensitive because traits are opaque, account-defined data. `default_value` and `hint` here are schema-level metadata (a field's default and help text), not account data — they are not masked, consistent with how `create_location`'s address fields or `create_document`'s `name` are not masked either. Nothing in this new tool's inputs is traits-shaped, so `_trait_secrets()` itself is not reused or extended.
- **In-scope cleanup:** none found — `flexible_assets.py`, `README.md`'s Flexible assets row, and `test_flexible_assets.py` have no unused code or stale comments in the lines this ticket touches.
- **Follow-ups (out of scope, not filed as separate tickets by this design):** update/bulk-update/delete for flexible asset fields are real IT Glue operations this connector still doesn't expose; not built here because neither the ticket nor the Rewst flow it replaces calls them (YAGNI). Worth a future gap-register pass if a Rewst flow is found that needs them.

### Data & API contract

Request (MCP tool call):

```
itglue_create_flexible_asset_field(
  flexible_asset_type_id: int,     // required; the type to add the field to
  name: string,                    // required; field label
  kind: string,                    // required; e.g. "Tag", "Text", "Textbox", "Checkbox", "Date",
                                    // "Number", "Select" -- not validated locally, see Open questions
  order?: int,                     // display order among the type's fields
  required?: bool,                 // whether the field must be filled in
  show_in_list?: bool,             // whether the field shows in the asset list view
  use_for_title?: bool,            // whether this field's value builds the asset's title
  tag_type?: string,               // for kind="Tag": the tag namespace, e.g. "Contacts"
  hint?: string,                   // help text shown next to the field
  default_value?: string           // default value for new records
) -> string (JSON)
```

Upstream call: `POST /flexible_asset_types/{flexible_asset_type_id}/relationships/flexible_asset_fields` with body `{"data": {"type": "flexible_asset_fields", "attributes": {<only the set fields, dasherized>}}}` via `api.attributes()` (`src/itglue_mcp/api.py:233-239`) — unset optional fields are omitted, same as every other create/update tool.

Response (success), the connector's standard single-item envelope (field names depend on exactly what IT Glue echoes back; at minimum `id`):

```json
{
  "id": "9001",
  "name": "Full Access Record",
  "kind": "Tag",
  "order": 860,
  "tag_type": "Contacts",
  "show_in_list": false
}
```

Response (error), same envelope every tool returns on failure: `{"error": {"code": "...", "message": "...", "retryable": false}}`, `code` one of `not_configured`, `unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error` (`src/itglue_mcp/api.py:39-57`).

**Backward compatibility:** purely additive. No existing tool's name, parameters or response shape changes. `tests/fixtures/tools_baseline.json` is widened (a new entry added), never narrowed — `test_tool_names_match_baseline` (`tests/test_tools.py:15-16`) requires the baseline and the live tool set to match exactly, so the baseline update ships in the same commit as the tool.

### Key flow / sequence

1. Agent Platform / gateway calls `itglue_create_flexible_asset_field` over MCP with the tenant's `X-ITGlue-API-Key` (+ optional region/base URL) headers, unchanged from every other call to this server.
2. `CredentialMiddleware` extracts and validates the headers (unchanged).
3. The new tool handler validates `flexible_asset_type_id` is numeric (`seg()`), builds the JSON:API body via `api.attributes("flexible_asset_fields", values)` with only the fields the caller passed, and calls `POST /flexible_asset_types/{id}/relationships/flexible_asset_fields` through the per-request `ITGlueClient`.
4. `api.item()` flattens the JSON:API response into the standard single-item envelope.
5. `run()` wraps any upstream error into the standard error envelope; nothing here is new.

### Non-functional

- **Security:** no change to the credential model — API key stays header-only, never persisted, never logged (`src/itglue_mcp/tools/_common.py:80-106`). None of this tool's inputs are traits-shaped secrets (see Reuse & cleanup decision above), so no `drop`/masking set is needed, unlike `passwords.py` or `create_flexible_asset`'s trait masking.
- **Multi-tenant isolation:** unaffected. One `ITGlueClient` is created per request, scoped to that request's own API key (`src/itglue_mcp/api.py:92-99`); a tenant can only ever add a field to a flexible asset type within its own IT Glue account. No new state is introduced that could leak across tenants or requests.
- **Performance:** a single upstream POST per call, bounded by the existing retry/backoff logic in `api.py:107-146` (3000 requests / 5 minutes IT Glue rate limit, already handled generically). No pagination involved.
- **Observability:** errors flow through the same `log.exception` / structured-envelope path as every other tool (`src/itglue_mcp/tools/_common.py:99-106`); nothing new to add.
- **Idempotency:** this is a non-idempotent create (`annotations=CREATE`, `idempotentHint=False`), same as `create_flexible_asset`/`create_location`/`create_document` — calling it twice with the same arguments creates two fields, matching IT Glue's own behaviour and every other create tool's annotation in this connector; the caller is responsible for not double-submitting.

### Rollout & rollback

Purely additive tool — no feature flag needed; adding a tool cannot break an existing caller. Ships via the standard MCP flow: merge to `main`, `mcppub publish` re-runs the full test suite on `main` before deploying, then redeploys to INT. Rollback is a revert of the merge commit followed by a re-publish — no data or schema to roll back (this repo is stateless; the only "data" this tool creates lives in the caller's own IT Glue account, outside this connector's control either way).

### Test strategy

- **Unit (new), `tests/test_flexible_assets.py`:**
  - Happy path: mocked `POST /flexible_asset_types/456/relationships/flexible_asset_fields` returning 201 with a field body; assert the request body matches `{"data": {"type": "flexible_asset_fields", "attributes": {...}}}` with every passed field, and the returned envelope has `id` (AC1).
  - Only-required-fields path: call with just `flexible_asset_type_id`, `name`, `kind`; assert the request body's `attributes` contains exactly those two keys (no `order`/`required`/etc.) (AC2).
  - Pass-through: call with `kind="Tag"`, `tag_type="Contacts"` (the gap register's own example); assert both values appear unchanged in the request body (AC3).
  - Invalid type ID: call with a non-numeric `flexible_asset_type_id`; assert `{"error": {"code": "invalid_argument"}}` without a request ever being sent (mirrors `seg()`'s existing behaviour, exercised today for other tools in `tests/test_argument_errors.py`).
  - Not found: mocked 404 on the same path; assert `{"error": {"code": "not_found"}}` (AC4).
- **Errors/credentials (inherited):** AC5 and AC6 are already covered generically by `test_missing_credentials_envelope` and `test_error_mapping` (`tests/test_handlers.py`), which exercise the shared `run()`/`ITGlueClient.request()` path this new tool reuses unmodified; no per-tool duplicate needed.
- **Contract (modify), `tests/fixtures/tools_baseline.json` + `tests/test_tools.py`:** add the new tool's baseline entry; this automatically extends `test_tool_names_match_baseline`, `test_parameters_are_backward_compatible`, `test_descriptions_are_concise`, and `test_no_agent_id_parameter` to cover it (part of AC7) — no new test code needed beyond the fixture entry. `test_annotations` is not extended for this tool specifically (it only spot-checks a fixed list of tool names today), so AC7's `readOnlyHint`/`destructiveHint` claim is instead checked directly in the new unit test that calls `mcp.list_tools()`.
- **Tool count (modify), `tests/test_middleware.py`:** update both hardcoded `37` assertions to `38`.
- **No real IT Glue account needed** for any of the above — all tests mock the HTTP layer with `respx`, same as every existing test in this repo. The INT publish step re-runs this suite before deploying, which is the closest thing to an integration check this repo has.

### Effort & breakdown

Small, single sub-task: ~35-50 lines in `flexible_assets.py`, a README table-row + behaviour-note update, one `tools_baseline.json` entry, a two-line `test_middleware.py` count fix, and 4-5 new unit tests. Estimated 0.5 day including review.

### Risks & dependencies

- No dependency on another ticket, no gateway change, no migration.
- The exact `kind` enum and the request body's `"type"` key are not pinned down by a fully reachable public spec for this specific endpoint (see Open questions); this design follows the connector's own established convention (unvalidated enum-like strings, `api.attributes()`'s `"type"` key) rather than inventing new policy, which keeps the risk bounded to "surfaces as a structured, mapped error at first real use" rather than silent failure.
- No live IT Glue account is available to verify behaviour end-to-end before INT; the dev leg's self-test is limited to mocked-HTTP unit tests plus the INT publish's own deploy/health check (same limitation every other tool in this connector has had, including PRD-21586 and PRD-21217).
