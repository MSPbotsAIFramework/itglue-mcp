## Product design

### Goals / Non-goals

**Goals**: add one new read-only tool that lets an agent fetch a single IT Glue flexible asset type by
ID and see its field (trait) definitions in the same call — closing the one gap the ticket names, and
matching what Rewst's `it_glue.get_flexible_asset_type` action already does for this customer.

**Non-goals**:
- Creating, updating or deleting flexible asset **types** (the schema itself). IT Glue flexible asset
  types are managed in the IT Glue UI; `list_flexible_asset_types` is already read-only by design, and
  PRD-21217 (the immediately preceding ticket on this same repo) already established this as an
  explicit non-goal for the connector. Nothing in this ticket's description asks for type
  creation/editing — it names one read tool.
- Changing `list_flexible_asset_types`'s existing behaviour (its lack of an `id` filter, or its
  ignoring `organization_id` — both pre-existing and out of scope here).
- Any change to flexible **assets** (data records) — `get_flexible_asset` /
  `create_flexible_asset` / `update_flexible_asset` already exist and are untouched.
- `contacts` — mentioned in the gap register's "现状与依据" line as also missing from this connector,
  but not named as this ticket's ask (`需补充的 tool: itglue_get_flexible_asset_type`, singular). Left
  for a future card if requested.

### Acceptance criteria

- **AC1**: Given a flexible asset type ID that exists in IT Glue, when the agent calls the new tool,
  then the response includes that type's ID, its name, and a `fields` list containing one entry per
  field IT Glue has defined for that type (at minimum each field's ID, name and kind).
- **AC2**: Given a flexible asset type ID that does not exist (or belongs to a different IT Glue
  account than the request's credentials), when the agent calls the tool, then the response is the
  structured `not_found` error envelope, not a raw HTTP error or a stack trace — matching every other
  `get_*` tool in this connector.
- **AC3**: Given a flexible asset type that has zero custom fields configured, when the agent calls
  the tool, then the response's `fields` list is an empty array — not an error, and not a missing key.
- **AC4 (credentials / tenant isolation)**: Given two requests that carry different
  `X-ITGlue-API-Key` values, when each calls the new tool, then each request only reads flexible asset
  type data belonging to the IT Glue account identified by *its own* header — the existing
  per-request credential model (`src/itglue_mcp/credentials.py`); the new tool introduces no
  module-level or cross-request state.

### Open questions

- [non-blocking, assumed] The one Rewst sub-flow cited as evidence is named "ITG: Upsert Flexible
  Asset Type". Read literally, "upsert...type" could suggest creating/editing the type's *schema*, not
  just reading it. This design assumes the sub-flow's name refers to upserting a flexible **asset** of
  that type (an existing, already-covered capability via `create_flexible_asset` /
  `update_flexible_asset`) and calls `get_flexible_asset_type` first to discover the type's field
  names before building the asset payload — not a request to make the type's schema writable. This
  reading is consistent with: (a) the gap register names exactly one missing tool, a read tool; (b)
  IT Glue flexible asset types have no public write endpoint in the connector's own cited developer
  docs reference, and PRD-21217 already recorded types as UI-managed. If this assumption is wrong,
  §"Goals / Non-goals" and the Change list below would need a much larger follow-up ticket for
  type-schema writes — not something to guess into this one.

## Tech design

### Conclusion

Add one tool, `get_flexible_asset_type`, to the existing
`src/itglue_mcp/tools/flexible_assets.py` module, following the same thin-wrapper shape every other
tool in this file and repo already uses: `api.ITGlueClient.get` + the JSON:API helpers in `api.py`,
registered through the module's existing `register(mcp, settings)` function (already wired into
`server.py`, no server-side registration change needed beyond the `INSTRUCTIONS` string, §4). The one
piece of new plumbing is a small `api.included()` helper — this is the first tool in the repo that
needs a JSON:API `include=` sideload, so there is nothing to reuse for that specific step, but the
helper is a direct sibling of the existing `api.flatten()`/`api.item()` and adds no new dependency.

### Option analysis

No real alternative for the tool's existence: the ticket names one specific missing vendor capability
(read one flexible asset type by ID, with its field definitions), and IT Glue's REST API exposes
exactly that as a single-item `GET /flexible_asset_types/{id}` call. The only design choice is how to
expose the field definitions:

| Option | Do | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Always request and return the field definitions (hardcode `include=flexible-asset-fields`, no toggle parameter) | One tool, one required parameter (`id`) | Matches the ticket's own description of what "the flow uses" (both `data.attributes.name` *and* `relationships.flexible-asset-fields` together); matches Rewst's single action `it_glue.get_flexible_asset_type`, which the ticket cites as already returning both; simplest possible surface (YAGNI — nothing in the ticket asks for a way to skip fetching fields) | A caller who only wants the type's name pays for fetching its fields too — negligible: this is a single bounded sideload on one resource, not a paginated list | **chosen** |
| B. Add an `include_fields: bool = True` parameter so a caller can opt out | Same default behaviour, plus an escape hatch | Marginally more flexible | New parameter nobody asked for, more surface to keep backward-compatible forever (`AGENTS.md:19`: once added, parameters cannot become required, and every parameter is a permanent compatibility commitment) for a saving (skipping one bounded sideload) that has no stated use case | rejected |
| C. Don't add a new tool; have the agent call `list_flexible_asset_types` and filter client-side | Reuse existing tool | No new code | Does not solve the ticket: `list_flexible_asset_types` has no `id` filter (`:39-42` sends no such param to IT Glue) and never requests `include=`, so it cannot return field definitions at all, at any page size | rejected — does not meet AC1 |

Chose A. Reuses 100% of the existing `ITGlueClient`/JSON:API plumbing; the only addition is the small
`included()` helper (below), which is itself a direct sibling of `flatten()`, not a new abstraction.

### Change list

- `src/itglue_mcp/api.py` [changed] — add `included(payload, type_=None)`: flattens the JSON:API
  `included` sideload array the same way `flatten()` already flattens `data` (snake_cases attribute
  keys), optionally filtered to one resource `type`. Placed next to `item()`/`page()` (`:176-221`).
  ```python
  def included(payload: dict[str, Any] | None, type_: str | None = None) -> list[dict[str, Any]]:
      """Flattened `included` sideload resources from a JSON:API response that used `?include=`."""
      rows = (payload or {}).get("included") or []
      if type_:
          rows = [r for r in rows if r.get("type") == type_]
      return [flatten(r) for r in rows]
  ```
- `src/itglue_mcp/tools/flexible_assets.py` [changed] — add `get_flexible_asset_type` to `register()`,
  next to the other flexible-asset tools:
  ```python

          "traits an asset of this type can have). Call this before create_flexible_asset or "
          "update_flexible_asset to see which trait names and kinds the type expects."

      annotations=READ,
      structured_output=False,

      id: Annotated[str, Field(description="Flexible asset type ID.")],
  ```

### Data & API contract

**`get_flexible_asset_type`**
```
GET /flexible_asset_types/{id}?include=flexible-asset-fields
```
Response (flattened by `api.item` + the new `api.included`; exact attribute set is whatever IT Glue
returns — this server does not rename or drop type/field attributes, same posture as every other
`get_*` tool here):
```json
{
  "id": "456",
  "name": "Active Directory",
  "enabled": true,
  "fields": [
    {"id": "1", "name": "Domain Name", "kind": "Text", "required": true, "order": 1},
    {"id": "2", "name": "Functional Level", "kind": "Text", "required": false, "order": 2}
  ]
}
```
Errors: `not_found` (404 — unknown id, or a type belonging to a different IT Glue account than the
request's credentials; IT Glue does not distinguish the two cases, same behaviour as every other
`get_*` tool in this repo), `unauthorized` (401/403 — bad/insufficient API key).

**Backward compatibility**: purely additive — one new tool name, no change to any existing tool's
name, parameters, or response shape. `tests/fixtures/tools_baseline.json` only gains one entry
(`AGENTS.md:19`'s "do not rename tools, remove parameters or add required parameters" rule is
respected for every tool that already exists).

**DB**: none — this server is stateless and has no database (`AGENTS.md:15`).

### Key flow / sequence

```
Agent -> MCP gateway -> itglue-mcp: get_flexible_asset_type(id="456")
itglue-mcp: GET https://api.itglue.com/flexible_asset_types/456?include=flexible-asset-fields
            (x-api-key from this request's X-ITGlue-API-Key header, per credentials.py)
IT Glue API -> itglue-mcp: 200 { data: {...type attrs...}, included: [...field objects...] }
itglue-mcp -> Agent: { id, name, ...other type attrs, fields: [...flattened field objects] }
```
A typical caller then uses the returned field `name`s as the keys of the `traits` object passed to
`create_flexible_asset` / `update_flexible_asset` (both already existing, unchanged by this ticket).

### Non-functional

- **Idempotency / concurrency**: read-only GET, trivially idempotent. No new concurrency concerns —
  each call opens its own `ITGlueClient` (`api.py:91`), nothing shared across calls, same as every
  other tool.
- **Performance**: single-resource GET with one bounded sideload (a flexible asset type's field count
  is small — IT Glue customers configure a handful to a few dozen fields per type, not pages of them);
  no pagination needed or added. Same per-call timeout/retry behaviour as every other tool
  (`Settings.read_timeout`, `Settings.connect_timeout`, retry on 429/5xx — `api.py:102-144`),
  unchanged.
- **Security**: credentials are read from `X-ITGlue-API-Key` per request, never persisted
  (`credentials.py`, unchanged). Type names and field definitions are schema metadata, not customer
  secrets or PII — same posture as `itglue_list_account_users`'s "no field dropping" decision
  (PRD-21586): nothing in this response needs masking, so no `secrets=` argument is passed to `run()`.
- **Multi-tenant isolation**: not applicable in the database sense (no database); the guarantee is
  per-request credential isolation (AC4), provided unchanged by the existing `ContextVar`-based
  `credentials.py`.
- **Observability**: unchanged — `_common.run` already logs unexpected errors without secrets
  (`_common.py:95-102`); nothing new to log since nothing new is secret.

### Risks & dependencies

- **Risk**: this design's assumption about the exact set of attributes IT Glue returns per flexible
  asset field (name, kind, required, order, etc.) comes from the JSON:API convention this repo's
  client already follows and from the ticket's own stated output fields, not from an independently
  re-verified live call (no test account — see Test strategy). No code risk follows from this: the
  server does not hardcode or rename field attributes (`flatten()` passes through whatever IT Glue
  sends), so if the real attribute set differs, the tool still works correctly — only this design doc's
  illustrative JSON example could be imprecise. Flagged, not treated as a blocker, same posture
  PRD-21217 used for its own unverified PATCH-merge assumption.
- **Risk**: the Open Questions assumption about "Upsert Flexible Asset Type" referring to asset-level
  upsert, not type-schema upsert (see Product design, Open questions). If wrong, a follow-up ticket
  would be needed — not a reason to block this one, since the gap register's literal ask is a single
  read tool.
- **Dependency**: none on other tickets or repos. Self-contained addition to `itglue-mcp`; no gateway
  change, no platform-repo change (`Track:` below).
