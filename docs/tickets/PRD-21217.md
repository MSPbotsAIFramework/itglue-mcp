## Product design

### Goals / Non-goals

**Goals**: close the one real gap found above — let an agent read a single flexible asset by ID,
create one, and update one (including setting its name, trait values, and archived flag). This makes
"manage" true for all four nouns in the ticket.

**Non-goals**:
- Deleting flexible assets. IT Glue flexible assets do not have a delete endpoint in the public API;
  the existing connector convention for anything destructive is archive, not delete
  (`INSTRUCTIONS` in `src/itglue_mcp/server.py:24-33`: "Prefer archive over delete"). `archived` is
  exposed as a field on `update_flexible_asset` instead of separate archive/unarchive tools (see
  Tech design §3 for why).
- Bulk/batch create or update. Nothing in the ticket asks for it, and no other tool in this repo
  does bulk writes.
- Any change to configurations, passwords, locations, documents, organizations, or attachments —
  all four of those areas are already fully covered; this ticket only touches flexible assets.
- Changing flexible asset **types** (schema definition) — out of scope; `list_flexible_asset_types`
  is read-only by design in IT Glue (types are managed in the IT Glue UI).

### Acceptance criteria

- **AC1**: Given a flexible asset ID that exists in IT Glue, when the agent calls the new
  "get one flexible asset" tool, then the response includes that asset's ID, name, organization,
  flexible asset type, archived flag, and its full set of trait values (the type's custom fields).
- **AC2**: Given a flexible asset ID that does not exist (or belongs to a different IT Glue account
  than the request's credentials), when the agent calls the tool, then the response is the
  structured `not_found` error envelope, not a raw HTTP error or a stack trace.
- **AC3**: Given an organization ID, a flexible asset type ID, and a set of trait values, when the
  agent calls the "create flexible asset" tool, then IT Glue has a new flexible asset of that type
  under that organization, and the tool's response includes the new asset's ID and the fields that
  were set.
- **AC4**: Given an existing flexible asset ID and one or more fields to change (name and/or trait
  values and/or archived), when the agent calls the "update flexible asset" tool, then only the
  fields passed are changed in IT Glue — fields not passed keep their previous value — and the
  response reflects the new state.
- **AC5**: Given an "update flexible asset" call with no fields to change at all, when the agent
  calls the tool, then the tool returns an `invalid_argument` error and makes no request to IT Glue
  (consistent with `update_password` / `update_location`'s existing guard).
- **AC6 (credentials / tenant isolation)**: Given two requests that carry different
  `X-ITGlue-API-Key` values, when each calls the new tools, then each request only reads or writes
  data in the IT Glue account identified by *its own* header — the server does not cache or reuse
  credentials or results across requests. This is the existing per-request credential model
  (`src/itglue_mcp/credentials.py`); the new tools must not introduce any module-level or
  cross-request state.
- **AC7 (secrets / logging)**: Given an error while creating or updating a flexible asset, when the
  error is returned or logged, then no trait value is assumed safe to omit from masking by default —
  trait values are opaque custom data (per-type schema can hold anything, including entries an
  account chose to store there), so the error envelope carries only IT Glue's own error `detail`
  text (as the other write tools already do), never the request's raw `traits` payload.

- [不阻塞] Whether to also expose `search_flexible_assets`'s missing `filter[archived]` (today it

## Tech design

### Conclusion

Add three tools to the existing `src/itglue_mcp/tools/flexible_assets.py` module — `get_flexible_asset`,
`create_flexible_asset`, `update_flexible_asset` — following the exact shape already used by
`configurations.py` / `locations.py` / `passwords.py` in this repo: thin wrappers around
`api.ITGlueClient` + the JSON:API helpers in `api.py`, registered through the module's existing
`register(mcp, settings)` function (already wired into `server.py:51-61`, no server-side change
needed). `archived` is exposed as an optional field on `update_flexible_asset` rather than as
separate archive/unarchive tools, because IT Glue's flexible-asset PATCH takes `archived` as one more
attribute (unlike `configurations`/`documents`, which the previous connector's tool surface already
split into dedicated archive/unarchive calls — flexible assets never had that split, and there is no
compatibility baseline requiring one, see §4a).

### Option analysis

No real alternative: IT Glue's Flexible Assets REST resource is `/flexible_assets` with GET-by-id,
POST and PATCH, exactly mirroring the shape of `passwords`/`locations`/`configurations` already
implemented here. The only choice is how to expose `archived`:

| Option | Do | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. `archived` as a field on `update_flexible_asset` | one update tool, `archived: bool | None` like any other field | fewer tools; matches the vendor API shape (archived is just another PATCH attribute) | agent could flip archived alongside unrelated field edits in one call without a dedicated "confirm before archiving" prompt path | **chosen** |
| B. Separate `archive_flexible_asset` / `unarchive_flexible_asset`, like `configurations`/`documents` | mirror the other two areas' split | consistent tool-naming pattern across areas | two more tools for a capability nothing in this ticket asked for; those two areas inherited the split from the *previous* IT Glue connector's compatibility baseline (`README.md:111-113`: "Tool names ... match the previous ... connector") — flexible assets never had that baseline entry, so there is nothing to stay compatible with | rejected — would be scope creation beyond the ticket and beyond the compatibility requirement that justified it elsewhere |

Both options reuse 100% of the existing `api.py` plumbing; no new dependency, no new HTTP client
behaviour.

### Data & API contract

**`get_flexible_asset`**
```
GET /flexible_assets/{id}
```
Response (flattened by `api.item`, same shape as `get_configuration`/`get_location`):
```json
{"id": "789", "name": "Primary AD Domain", "organization_id": 123, "flexible_asset_type_id": 456,
 "traits": {"domain-name": "corp.example.com", "forest-functional-level": "2016"},
 "archived": false, "created_at": "...", "updated_at": "..."}
```
Errors: `not_found` (404, wrong id or wrong IT Glue account for the request's credentials —
IT Glue returns 404 for both, it does not distinguish; same behaviour as every other `get_*` tool
in this repo), `unauthorized` (401/403, bad/insufficient API key).

**`create_flexible_asset`**
```
POST /flexible_assets
{"data": {"type": "flexible_assets",
          "attributes": {"organization-id": 123, "flexible-asset-type-id": 456,
                          "name": "Primary AD Domain", "traits": {"domain-name": "corp.example.com"}}}}
```
`organization_id` and `flexible_asset_type_id` are required (IT Glue rejects a flexible asset not
tied to an organization and a type); `name` and `traits` are optional at the API level but at least
one of them should normally be sent — not enforced server-side beyond what IT Glue itself requires,
same posture as `create_location`. Response: the created record, same flattened shape as above.
Errors: `invalid_argument` (422, e.g. unknown `flexible_asset_type_id`, or a trait name IT Glue
does not recognise for that type), `not_found` (organization_id does not exist), `unauthorized`.

**`update_flexible_asset`**
```
PATCH /flexible_assets/{id}
{"data": {"type": "flexible_assets",
          "attributes": {"name": "Primary AD Domain (renamed)", "archived": true}}}
```
Only attributes present in the request body are sent (`api.attributes` already drops `None` values,
`locations.py:166-167`'s guard pattern is reused to refuse an all-`None` call before making any HTTP
call). `traits` is replace-by-key at the IT Glue API level: IT Glue merges the posted traits object
into the existing one at the key level (vendor behaviour, not something this server controls), so a
caller does not need to resend unrelated trait keys. Response: the updated record, flattened.
Errors: `invalid_argument` (no fields passed — handled locally, §above; or IT Glue 422), `not_found`,
`unauthorized`.

**Backward compatibility**: purely additive — three new tool names, no change to any existing tool's
name, parameters, or response shape. `tests/fixtures/tools_baseline.json` only gains entries; nothing
is removed from it, so the `AGENTS.md:19` rule ("Do not rename tools, remove parameters or add
required parameters") is respected for every tool that already exists.

**DB**: none — this server is stateless and has no database (`AGENTS.md:15`: "no module-level
mutable state").

### Key flow / sequence

```
Agent -> MCP gateway -> itglue-mcp: create_flexible_asset(organization_id, flexible_asset_type_id, traits)
itglue-mcp: build JSON:API body (api.attributes) -> POST https://api.itglue.com/flexible_assets
            (x-api-key from this request's X-ITGlue-API-Key header, per credentials.py)
IT Glue API -> itglue-mcp: 201 + the created resource
itglue-mcp -> Agent: flattened JSON (id, name, organization_id, flexible_asset_type_id, traits, archived)
```
Update and get-by-id follow the same shape with PATCH/GET instead of POST.

### Non-functional

- **Idempotency / concurrency**: `create_flexible_asset` is not idempotent — calling it twice creates
  two records, identical to `create_password`/`create_location` today; this is the vendor API's own
  behaviour (no client-supplied idempotency key exists in IT Glue's flexible-assets endpoint). An
  agent that wants to avoid duplicates should `search_flexible_assets` first, same guidance already
  given for passwords (`passwords.py:111`). `update_flexible_asset` is idempotent (PATCH with the
  same body twice yields the same end state). No new concurrency concerns: each tool call opens its
  own `ITGlueClient` (`api.py:91`), nothing is shared across calls.
- **Performance**: single-record GET/POST/PATCH, no pagination involved. Same per-call timeout/retry
  behaviour as every other tool (`Settings.read_timeout`, `Settings.connect_timeout`, retry on
  429/5xx — `api.py:102-144`), unchanged.
- **Security**: credentials are read from `X-ITGlue-API-Key` per request, never persisted
  (`credentials.py`, unchanged by this ticket). `traits` values are treated as opaque custom data,
  not specially masked like `password` fields are (`passwords.py:120,157` use `SECRET_SCHEMA` and
  `run(..., secrets=[password])`) — this ticket does not introduce a new secret-bearing field, so no
  masking parameter is added. Error messages reuse `_status_to_error`'s existing `detail` extraction
  (`api.py:60-73`), which already only surfaces IT Glue's own error text, not the request body.
- **Multi-tenant isolation**: not applicable in the database sense (this server has no database); the
  equivalent guarantee is per-request credential isolation (AC6), which the existing
  `ContextVar`-based `credentials.py` already provides and these new tools do not change.
- **Observability**: unchanged — `_common.run` already logs unexpected errors
  (`_common.py:95-100`) without secrets; no new logging needed since `traits` carries no fields this
  server treats as secret.

### Effort & breakdown

1–2 person-days: three tools following an established in-repo pattern, README/INSTRUCTIONS/baseline
updates, and unit tests. No sub-task split needed — this is a single small, additive change
to one module; splitting it would just add handoff overhead.

### Risks & dependencies

- **Risk**: IT Glue's PATCH trait-merge behaviour (merges posted trait keys into the existing object
  rather than replacing it wholesale) is vendor behaviour this server does not control and this
  design did not independently verify against a live account (no test account, see Test strategy).
  If a future real-account test shows IT Glue instead *replaces* the whole `traits` object on PATCH,
  the tool description and AC4 wording ("only the fields passed are changed") would need a follow-up
  correction — low risk, but flagged so it is not silently assumed.
- **Dependency**: none on other tickets or repos. This is a self-contained addition to
  `itglue-mcp`; no gateway change, no platform-repo change (`Track:` below).
