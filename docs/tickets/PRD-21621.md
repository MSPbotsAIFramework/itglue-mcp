## Requirement understanding

One line: Add a tool to create an IT Glue flexible asset under an organization, accepting organization_id, flexible_asset_type_id and traits as required inputs and archived and restricted as optional inputs, matching the Rewst "IT Glue: Create Flexible Asset" action currently used by EMD Networking Services' flows.

The ticket is item 58 of a Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It
names the Rewst account (EMD Networking Services), the two live Rewst flows that use this action in
the last 365 days ("Store BitLocker Keys in ITG Flexible Asset"; "ITG: Upsert Flexible Asset", a
sub-flow of "Document M365 Environment", evidence grade B), the HTTP method/endpoint, the full input
parameter list (required: `organization_id`, `flexible_asset_type_id`, `traits`; optional:
`archived`, `restricted`), the two response fields the Rewst flow actually reads (`data.id`,
`attributes.traits`), and a snapshot of MSPbots' tool coverage **as verified on 2026-10-28**: "the
same connector's 33 tools only have `list_flexible_asset_types` / `search_flexible_assets`; no
create, update, or get-by-id". It reports no bug and does not ask for anything beyond closing this
one gap.

## Product design

### Goals / Non-goals

**Goals**: let `create_flexible_asset` set `archived` and `restricted` at creation time, so a
migrated Rewst flow (or any agent) can create a flexible asset with these two flags already set
instead of creating it and then immediately calling `update_flexible_asset` to set them.

**Non-goals**:
- Adding `restricted` to `update_flexible_asset`. The vendor API supports it there too (Current
  state, above), but this ticket's Rewst evidence is about the **create** action only — neither
  cited Rewst flow calls an IT Glue update/upsert-via-PATCH action with `restricted`. Listed as a
  follow-up below, not built here, so as not to fold an unrequested change into this ticket's scope.
- Renaming any tool. The ticket's own gap-register template names the wanted capability
  `itglue_create_flexible_asset`, but this repo's actual create tool is `create_flexible_asset` (no
  prefix) — see Tech design §Option analysis for why the existing name is kept.
- Any change to `organization_id`, `flexible_asset_type_id`, `traits`, or `name` on
  `create_flexible_asset` — all four are already correct per the vendor API and the ticket's own
  parameter list.
- Any change to `get_flexible_asset`, `search_flexible_assets`, or `list_flexible_asset_types` —
  not mentioned by this ticket.

### Acceptance criteria

- **AC1**: Given `organization_id`, `flexible_asset_type_id` and `traits` (no `archived`, no
  `restricted`), when `create_flexible_asset` is called, then the request sent to IT Glue and the
  tool's response are unchanged from today — this ticket's two new parameters must not alter
  existing callers' behaviour.
- **AC2**: Given `archived=true` passed to `create_flexible_asset` alongside the required fields,
  when it is called, then the POST body sent to IT Glue includes `"archived": true`, and the
  response (the created record) reflects `archived: true`.
- **AC3**: Given `restricted=true` passed to `create_flexible_asset`, when it is called, then the
  POST body sent to IT Glue includes `"restricted": true`, and the response reflects
  `restricted: true`.
- **AC4**: Given `archived` and/or `restricted` are not passed (left at their default), when
  `create_flexible_asset` is called, then neither key appears in the POST body sent to IT Glue
  (same "only send what was set" convention `update_flexible_asset` already uses for `archived`,
  `flexible_assets.py:143` + `api.attributes`'s `None`-drop).
- **AC5**: Given a `traits` value that is an HTML string (e.g.
  `{"rewst-org-variables": "<table>...</table>"}`), when `create_flexible_asset` is called, then the
  value is forwarded to IT Glue unmodified (not escaped, stripped, or rejected) — confirms the
  existing opaque-`dict[str, Any]` handling (Current state, above) still holds with the new
  parameters added.
- **AC6 (credentials / tenant isolation)**: Given two requests that carry different
  `X-ITGlue-API-Key` values, when each calls `create_flexible_asset` with `archived`/`restricted`,
  then each request only writes to the IT Glue account identified by *its own* header — unchanged
  from the existing per-request credential model (`src/itglue_mcp/credentials.py`); the new
  parameters must not introduce any module-level or cross-request state.
- **AC7 (secrets / logging)**: Given an error during `create_flexible_asset` while a trait value
  looks like a credential, when the error is returned or logged, then the trait value is still
  masked (existing `_trait_secrets` behaviour, `flexible_assets.py:23-26`) — adding two plain
  boolean parameters must not change this, since neither `archived` nor `restricted` is itself
  secret-bearing.

### Open questions

- [non-blocking] **Tool name**: the ticket's gap-register line item is titled
  `itglue_create_flexible_asset`, but the repository's actual tool is `create_flexible_asset` (no
  prefix). Proceeding on the assumption that the ticket names the *capability*, not a literal
  required Python-level tool name — the gap register's own naming convention prefixes every line
  item with the connector's short name (`itglue_...`) regardless of what the underlying tool is
  actually called; `AGENTS.md:19` forbids renaming tools agents already depend on, and this repo's
  own precedent (PRD-21217's `create_flexible_asset`, not `itglue_create_flexible_asset`) treats the
  existing unprefixed name as the one to extend, not replace. If the requester specifically needs a
  tool literally named `itglue_create_flexible_asset` (e.g. because some other integration maps on
  that exact string), say so in a comment and move this ticket back to `5b - ready for groom`.
- [non-blocking] **`restricted` on `update_flexible_asset`**: flagged under Non-goals above as a
  real, same-shaped gap this ticket does not close (not requested by either cited Rewst flow). Worth
  a follow-up ticket for symmetry with `archived` if a future Rewst flow needs it.

## Tech design

### Conclusion

Add two optional parameters, `archived: bool | None = None` and `restricted: bool | None = None`,
to the existing `create_flexible_asset` tool in `src/itglue_mcp/tools/flexible_assets.py`, following
exactly the pattern `update_flexible_asset` already uses for `archived` on the same module
(`flexible_assets.py:141,143`): plain `Annotated[bool | None, Field(...)]` parameters folded into the
`values` dict that `api.attributes()` turns into the POST body, `None` values dropped automatically.
No new tool, no new file, no new dependency, no server-side change outside this one function.

### Where the current implementation lives

- `src/itglue_mcp/tools/flexible_assets.py:101-126` — `create_flexible_asset`, the function to
  extend.
- `src/itglue_mcp/tools/flexible_assets.py:128-151` — `update_flexible_asset`, the closest analogue:
  already has an `archived: bool | None` parameter folded into its `values` dict exactly the shape
  this ticket needs to add to `create_flexible_asset`.
- `src/itglue_mcp/api.py:233-239` (`api.attributes`) — builds the JSON:API body, dasherizes keys,
  drops `None` values; reused unchanged.
- `src/itglue_mcp/api.py:176-180` (`api.item`) — flattens the IT Glue response back to snake_case;
  reused unchanged, so `archived`/`restricted` will appear in the response the same way `archived`
  already does on `get_flexible_asset`/`update_flexible_asset` responses today, with no code change
  needed on the read side.
- `README.md:107` — the tool table row; no name or tool-list change needed (no new tool), but the
  "Behaviour notes" list (`README.md:110-126`) should gain one line documenting that `create_
  flexible_asset` now also accepts `archived`/`restricted`, matching the existing convention of
  documenting non-obvious parameter behaviour there (e.g. the `update_flexible_asset` trait-merge
  note).
- `tests/test_flexible_assets.py:48-64` (`test_create_flexible_asset_happy_path`) — the existing
  create test to extend, plus new tests for the two new parameters and the omitted-means-absent
  case (AC4).
- `tests/fixtures/tools_baseline.json` — `create_flexible_asset`'s entry currently lists `params:
  [flexible_asset_type_id, name, organization_id, traits]`. `tests/test_tools.py:19-25`'s
  compatibility check only requires the baseline's `params` to be a *subset* of the live schema and
  the live `required` to be a *subset* of the baseline's `required` — so adding two new optional
  parameters passes this check with **no baseline edit required**. Recommended anyway (dev leg) for
  the baseline to stay an accurate description of the tool, same spirit as PRD-21217 adding entries
  for its three new tools — but this is a documentation nicety, not a compatibility requirement.

### Data & API contract

**`create_flexible_asset`** (extended)

```
POST /flexible_assets
{"data": {"type": "flexible_assets",
          "attributes": {"organization-id": 123, "flexible-asset-type-id": 456,
                          "traits": {"rewst-org-variables": "<table>...</table>"},
                          "archived": false, "restricted": true}}}
```

`archived` and `restricted` are omitted from the body entirely when not passed (AC4), identical to
how `name`/`traits` are already optional today. Response: the created record, flattened by
`api.item` exactly as today — `archived` and `restricted` will appear in the response if and only if
IT Glue returns them (it already returns `archived` today per the existing test fixture's `asset()`
helper, `tests/test_flexible_assets.py:21-27`; `restricted` is expected to appear the same way once
sent, since `api.item`/`flatten` copy through every attribute IT Glue returns without an allowlist —
`api.py:163-173`).

**Backward compatibility**: purely additive — two new optional parameters on one existing tool, no
change to any other tool's name, parameters, or response shape, no new required parameter
(`AGENTS.md:19`).

**DB**: none — stateless server, no database (`AGENTS.md:15`).

### Key flow / sequence

```
Agent -> MCP gateway -> itglue-mcp: create_flexible_asset(organization_id, flexible_asset_type_id,
                                                            traits, archived?, restricted?)
itglue-mcp: build JSON:API body (api.attributes, archived/restricted included only if passed)
            -> POST https://api.itglue.com/flexible_assets
            (x-api-key from this request's X-ITGlue-API-Key header, per credentials.py)
IT Glue API -> itglue-mcp: 201 + the created resource (incl. archived, restricted if sent)
itglue-mcp -> Agent: flattened JSON (id, name, organization_id, flexible_asset_type_id, traits,
                                      archived, restricted)
```

### Non-functional

- **Idempotency / concurrency**: unchanged — `create_flexible_asset` is still not idempotent
  (calling it twice still creates two records; this is vendor behaviour, not something these two new
  parameters affect). No new concurrency concerns: each call still opens its own `ITGlueClient`
  (`api.py:91`).
- **Performance**: no change — same single-record POST, no pagination, same retry/timeout behaviour
  (`api.py:102-144`).
- **Security**: `archived` and `restricted` are plain booleans, not secret-bearing — they are not
  added to `_trait_secrets` (`flexible_assets.py:23-26`), which continues to scan only `traits`
  values, unchanged. Credentials remain per-request from `X-ITGlue-API-Key`
  (`credentials.py`, unchanged).
- **Multi-tenant isolation**: unchanged (AC6) — no database, so the only isolation guarantee is the
  existing per-request `ContextVar`-based credential model, which these two new parameters do not
  touch.
- **Observability**: unchanged — `_common.run` already logs unexpected errors without secrets
  (`_common.py:95-100`); no new logging needed, since neither new parameter is secret-bearing.

### Rollout & rollback

No feature flag in this repo (MCP tools are always-on once merged to `main` and deployed, per
`references/mcp-track.md` in the pipeline skill). Rollout: merge to `main` → publish to INT via
`mcppub publish` (review leg). Rollback: revert the merge commit, publish again — the two parameters
simply disappear from `create_flexible_asset`'s schema; nothing else depends on them yet (purely
additive), so there is no migration or data concern in either direction.
