## Requirement understanding

One line: Add the ability to update an IT Glue flexible asset's organization_id and restricted attributes (in addition to the already-supported traits/name/archived), so the Rewst it_glue.update_flexible_asset action (PATCH /flexible_assets/{id}) can be fully replicated on the MSPbots IT Glue MCP connector.

This ticket comes from the Rewst → MSPbots migration gap register (item 59), flagging the account "EMD Networking Services" as a real-world caller of this capability (365-day Rewst execution history, evidence grade B). The ticket names one specific tool and one specific gap (missing `organization_id` and `restricted` on update), not a general "add more IT Glue coverage" ask.

## Current state (every claim carries path:line, read at MSPbotsAIFramework/itglue-mcp@788bcac)

- The connector already has an `update_flexible_asset` tool: `src/itglue_mcp/tools/flexible_assets.py:128-151`. Signature: `update_flexible_asset(id, name=None, traits=None, archived=None)`. It sends a `PATCH /flexible_assets/{id}` with only the non-`None` fields (`src/itglue_mcp/api.py:233-239` `attributes()` drops unset values and dasherizes keys), and rejects a call where every field is `None` with a structured `invalid_argument` error (`flexible_assets.py:146-147`).
- This tool was added on 2026-10-30 for PRD-21217 (`docs/changes/2026-10-30-flexible-asset-management.md`), which explicitly scoped it to `id, name, traits, archived` — `organization_id` and `restricted` were not in scope for that ticket and are not implemented.
- README's tool table already lists `update_flexible_asset` under "Flexible assets" (`README.md:112`), and the README states tool names mirror the *previous* IT Glue connector on the platform, mostly without an `itglue_` prefix (`README.md:115-116`). The Rewst action name in this ticket, `itglue_update_flexible_asset`, is Rewst/gap-register terminology for the vendor operation, not a name this connector is expected to expose verbatim — the equivalent connector tool is `update_flexible_asset`.
- IT Glue's own API (confirmed via the public developer docs at https://api.itglue.com/developer/, read 2026-10-31) accepts `organization_id` and `restricted` as optional, nilable attributes on both create and update of a flexible asset, alongside `name`, `traits` and `archived` — the same resource `update_flexible_asset` already PATCHes.
- `tests/fixtures/tools_baseline.json:363-373` is the compatibility baseline the platform relies on for this tool: `params: [archived, id, name, traits]`, `required: [id]`. `AGENTS.md:24-25` states the project must not rename tools, remove parameters, or add *required* parameters — adding new *optional* parameters is explicitly allowed and is enforced as backward-compatible by `tests/test_tools.py:18-23` (`test_parameters_are_backward_compatible` only requires the baseline's params to be a subset of the live schema, and the baseline's required set to be a subset of the live required set).
- `flatten()` (`src/itglue_mcp/api.py:163-173`) generically maps every attribute IT Glue returns (dash→underscore) into the tool's JSON response — so once `organization_id`/`restricted` are sent and IT Glue echoes them back, they will appear in the response with no change needed to the read path (`get_flexible_asset`, `update_flexible_asset`'s own return value).

**Conclusion so far**: the capability this ticket asks for is 90% already built. The actual gap is two missing optional parameters on one existing tool, not a missing tool.

## Product design

### Goals / Non-goals

**Goals**:
- `update_flexible_asset` accepts `organization_id` and `restricted` as new optional parameters, sent to IT Glue only when the caller provides them (consistent with how `name`/`traits`/`archived` already behave).
- No existing caller behavior changes: a call that only passes `id` + any of the current four fields behaves exactly as before.

**Non-goals**:
- No new tool is added. No other flexible-asset tool (`list_flexible_asset_types`, `search_flexible_assets`, `get_flexible_asset`, `create_flexible_asset`) is changed — the ticket's gap is specifically about the update operation. (`create_flexible_asset` already accepts `organization_id` as a required creation-time field; this ticket does not touch it.)
- No change to error handling, retry, credential, or pagination behavior.
- No change to any other connector (this ticket's Code Repo is MSPbotsAIFramework/itglue-mcp only).

### Acceptance criteria

- **AC1 (new capability — organization_id)**: Given a valid flexible asset `id`, when `update_flexible_asset` is called with `organization_id` set (and no other field), then the PATCH request to IT Glue carries `organization-id` as the only attribute, and the tool's response reflects whatever IT Glue returns for that asset (including `organization_id` if IT Glue echoes it).
- **AC2 (new capability — restricted)**: Given a valid flexible asset `id`, when `update_flexible_asset` is called with `restricted=true` (and separately, `restricted=false`), then the PATCH request carries `restricted` as `true`/`false` respectively, and the response reflects IT Glue's returned value. (`False` must not be dropped as if it were "not provided" — only `None` means "not provided".)
- **AC3 (combination)**: Given a valid `id`, when `update_flexible_asset` is called with a mix of old and new fields (e.g. `traits` + `organization_id`, or `archived` + `restricted`), then the PATCH request carries exactly the fields passed, nothing more.
- **AC4 (backward compatibility, regression)**: Given a valid `id`, when `update_flexible_asset` is called with only the pre-existing fields (`name`/`traits`/`archived`), then the PATCH payload is unchanged from today (no `organization-id` or `restricted` key appears).
- **AC5 (empty-call rejection, regression)**: Given a valid `id`, when `update_flexible_asset` is called with none of `name`, `traits`, `archived`, `organization_id`, `restricted` set, then the tool returns the structured `invalid_argument` error ("Pass at least one field to change.") without making an HTTP call — this must keep working now that there are five optional fields instead of three.
- **AC6 (not found, regression)**: Given an `id` that does not exist in IT Glue, when `update_flexible_asset` is called with any valid field (old or new), then the tool returns the structured `not_found` error, unchanged from today.
- **AC7 (isolation, SOP's stateless/header-only rule, not a new behavior but must not regress)**: This change adds no module-level state and reads no new credential; per-request isolation (`src/itglue_mcp/credentials.py`, unchanged) is unaffected. Verified by the fact that no new global/shared state is introduced in the change list below, and by the existing `creds` fixture being reused in the new tests unchanged.

### Open questions

- None that block implementation. One non-blocking assumption: the ticket's field list does not specify the input type for `restricted` on the MCP side; IT Glue's docs describe it as boolean (`true/false/1/0`). This design treats it as `bool | None`, matching `archived`'s existing representation on this same tool (`flexible_assets.py:141`) — if a future caller needs the legacy `0/1` integer form, IT Glue's JSON:API layer already accepts a Python `bool`, so no further change should be needed; flagged here only so the choice is visible, not because it is in doubt.

## Tech design

### Conclusion

Extend the existing `update_flexible_asset` tool in `src/itglue_mcp/tools/flexible_assets.py` with two new optional parameters, `organization_id: int | None` and `restricted: bool | None`, included in the same `values` dict that already feeds `api.attributes()`. No new tool, no new module, no new dependency.

### Where the current implementation lives

- Tool definition and handler: `src/itglue_mcp/tools/flexible_assets.py:128-151`.
- JSON:API request building (dasherize + drop-`None`): `src/itglue_mcp/api.py:233-239`.
- JSON:API response flattening (generic, no per-field mapping needed): `src/itglue_mcp/api.py:163-173`.
- Compatibility baseline enforced by tests: `tests/fixtures/tools_baseline.json:363-373`, checked by `tests/test_tools.py:18-23`.
- Existing tool tests: `tests/test_flexible_assets.py` (see `test_update_flexible_asset_*`, lines ~79-110).

### Option analysis

- **Option A (chosen): add two optional parameters to the existing `update_flexible_asset` tool.** Minimal diff; reuses the existing dasherize/drop-`None` request builder and the existing generic response flattener unchanged; matches `AGENTS.md`'s explicit rule that optional parameters may be added to existing tools but required ones may not, and that tools must not be renamed. Zero new dependencies.
- **Option B (rejected): add a new, separate tool literally named `itglue_update_flexible_asset`.** The ticket's tool name is Rewst/gap-register terminology for the *vendor action*, not a name this connector must expose — the connector's own convention (stated in its README) is to reuse the legacy connector's unprefixed tool names, and `update_flexible_asset` already is that tool for this exact IT Glue endpoint (`PATCH /flexible_assets/{id}`). A second tool doing the same PATCH with near-identical parameters would duplicate the request-building and error-handling logic, give agents two tools for one operation (ambiguous tool selection), and violate the "avoid duplication / don't over-design" rule from the skill's global code-quality bar. Rejected.
- **Option C (rejected): expose `organization_id` and `restricted` as a generic passthrough `extra_attributes: dict` parameter instead of two named parameters.** Rejected for consistency: every other field on this tool (and on `create_flexible_asset`) is a named, typed, documented parameter; a generic bag would let a caller send arbitrary IT Glue attributes with no validation or description, is harder for an agent to discover via the tool schema, and is inconsistent with how `traits` (the one genuinely open-ended field on this resource) is already named and documented as such.

### Data & API contract

Tool signature (MCP `tools/call`):

```
update_flexible_asset(
  id: str,                      # required, unchanged
  name: str | None = None,      # unchanged
  traits: dict | None = None,   # unchanged
  archived: bool | None = None, # unchanged
  organization_id: int | None = None,  # NEW
  restricted: bool | None = None,      # NEW
) -> str   # JSON string, unchanged envelope
```

Outbound IT Glue call (unchanged shape, new possible attribute keys):

```
PATCH /flexible_assets/{id}
Content-Type: application/vnd.api+json
{
  "data": {
    "type": "flexible_assets",
    "attributes": {
      // only keys for parameters that were not None, e.g.:
      "organization-id": 42,
      "restricted": true
    }
  }
}
```

Error envelope (unchanged, from `src/itglue_mcp/api.py`): `{"error": {"code": ..., "message": ..., "retryable": bool}}`, `code` one of `not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`. If IT Glue were to reject either new attribute for a given account's permission level, it surfaces as the existing `invalid_argument` (400/422) mapping — no new error-handling code needed.

Response: unchanged shape; `organization_id`/`restricted` will appear in the flattened response automatically once sent and echoed back by IT Glue, same as every other attribute on this resource.

Backward compatibility: a caller that never passes the two new parameters gets byte-for-byte the same request and response as before this change. Verified by AC4.

### Key flow / sequence

1. Agent (or Rewst-equivalent workflow) calls `update_flexible_asset(id="...", traits={...}, organization_id=42)`.
2. Tool builds `values = {name, traits, archived, organization_id, restricted}`, drops `None`s via `api.attributes()`.
3. If all five are `None` → `ToolInputError` → `invalid_argument` envelope, no HTTP call (AC5).
4. Otherwise → `client.patch(f"/flexible_assets/{id}", body)` → IT Glue.
5. IT Glue responds 200 with updated resource, or 404/4xx/5xx → mapped via `_status_to_error` (unchanged).
6. Response flattened via `api.item()` → JSON string returned to the caller.

No new branching, no new external call, no new persisted state.

### Non-functional

- **Idempotency/concurrency**: unchanged — PATCH with a fixed set of attributes is already idempotent per call; no new concurrency surface introduced (`UPDATE` tool annotation, `idempotentHint=True`, `_common.py:24`, remains correct).
- **Performance**: no additional IT Glue calls; same single PATCH. Two more optional scalar/boolean parameters have no measurable overhead.
- **Security**: `organization_id` is an integer IT Glue org ID (not a secret); `restricted` is a boolean. Neither needs the trait-secret masking applied to `traits` (`_trait_secrets`, `flexible_assets.py:23-26`). Credentials continue to come only from per-request headers (`credentials.py`, untouched) — this ticket does not add any module-level or cross-request state, satisfying the SOP's "stateless, request-isolated" rule (AC7).
- **Multi-tenant isolation**: the connector has no cross-tenant state to isolate (stateless, per-request credentials); this change does not introduce any shared or cached state, so there is nothing new to isolate.
- **Logging/observability**: no new log statements needed; existing error-path logging (which already masks trait values) is unaffected since the two new fields are never secret-shaped.

### Rollout & rollback

- Pure code change on the connector's own repo; ships by merging `dev/PRD-21622` into `main`, then one `/api/deploy-int` publish of `main` (per `mcp-track.md` §3 — handled by the review leg, not this design).
- Backward compatible (AC4), so no coordinated rollout with any other repo is needed. `release order: none (single repo, no cross-repo dependency)`.
- Rollback: revert the one commit; the tool reverts to its pre-PRD-21622 three-optional-field shape. No data migration, no IT Glue-side state to roll back (the only state is whatever an actual PATCH call already changed on IT Glue's side, same as today).

### Effort & breakdown

### Risks & dependencies

- **Risk**: IT Glue could, for some account configurations, reject `organization_id` or `restricted` on PATCH (e.g., a plan without the "restricted assets" feature). Mitigated by the existing generic error mapping (`invalid_argument` is already a defined, structured outcome) — no special-casing needed, but worth calling out so a reviewer doesn't expect this PR to add IT Glue-side validation.
- **Dependencies**: none on other tickets or other repos. `Track: vendor-mcp` only; Code Repo is a single repository (`MSPbotsAIFramework/itglue-mcp`), so there is no cross-repo release ordering question.
