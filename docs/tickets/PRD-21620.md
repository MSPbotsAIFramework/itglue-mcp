## Requirement understanding

One line: Add a new tool to the IT Glue MCP connector that creates a flexible asset type (and its fields) in IT Glue, so the Rewst flow that today calls `it_glue.create_flexible_asset_type` (used by EMD Networking Services to provision types such as "BitLocker (Rewst)" and "Rewst Org Variables") can be rebuilt as an MSPbots agent.

This ticket is item 57 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It targets the `EMD Networking Services` Rewst account, which runs two flows that call IT Glue's "create flexible asset type" action — `[ROC] ITG: Store Org Vars ITG` (358 runs/365d) and `[EMD] BitLocker Recovery key backup` (26 runs/365d), both evidence grade A. The gap is that the MSPbots IT Glue connector has tools to list, search, read, create and update *flexible assets* (records of a type) but no tool to create the *type* itself — the two Rewst flows create a brand-new flexible asset type (with its field definitions) before they can write asset records against it.

## Product design

### Goals / Non-goals

**Goals**

- Add one new write tool, `itglue_create_flexible_asset_type`, that creates a flexible asset type in the authenticated IT Glue account, with `name` required and `enabled`/`description`/`icon` optional, matching the capability the ticket asks for.
- Let the same call optionally create the type's fields (name, kind, and the other per-field attributes the ticket lists) in one request, since both Rewst flows this ticket replaces always create a type together with its fields in a single action call.
- Keep the error behaviour identical to every other write tool in this connector: structured envelope, no unhandled exception, retries on transient failures.

**Non-goals**

- No tool to create/read/update a *single field* independently of creating the type (e.g. "add a field to an existing type later") — the ticket and the two Rewst flows it replaces only ever create fields at type-creation time.
- No tool to update or delete a flexible asset type — the ticket only asks for creation.
- No change to any existing tool's name, parameters, or behaviour.
- No UI change — this is a connector-level (MCP) change, not an Agent Platform page.
- No new connector and no gateway change — the repo already exists and this is an in-repo addition.

### Acceptance criteria AC1..ACn

- **AC1** — Given a valid `name` and no other parameters, when `itglue_create_flexible_asset_type` is called, then it creates a flexible asset type in IT Glue (`POST /flexible_asset_types` with only `attributes.name` set) and returns the created type's `id` and `name`.
- **AC2** — Given `name`, `enabled`, `description` and `icon` are all passed, when `itglue_create_flexible_asset_type` is called, then all four are forwarded as `data.attributes` on the upstream request, and unset optional parameters are omitted (not sent as `null`), matching every other create/update tool in this connector.
- **AC3** — Given a `fields` list is passed (each item carrying at least `name` and `kind`, optionally `order`, `required`, `show_in_list`, `use_for_title`, `tag_type`, `hint`, `default_value`), when `itglue_create_flexible_asset_type` is called, then the upstream request carries `data.relationships.flexible-asset-fields.data[]`, one entry per field, with that field's attributes forwarded unchanged in value (case handling per Tech design §5).
- **AC4** — Given `fields` is omitted or an empty list, when `itglue_create_flexible_asset_type` is called, then the upstream request has no `relationships` block at all (not an empty array) — IT Glue creates the type with zero fields, same as the ticket's "创建 IT Glue 灵活资产类型及其字段" being optional on the field side.
- **AC5** — Given a `fields` entry is missing `name` or `kind`, when `itglue_create_flexible_asset_type` is called, then it returns `{"error": {"code": "invalid_argument", ...}}` **before** any request reaches IT Glue (same local-validation posture as `update_flexible_asset`'s "pass at least one field" check), naming which field position is invalid.
- **AC6** — Given missing or invalid IT Glue credentials, when `itglue_create_flexible_asset_type` is called, then it returns the same structured error envelope as every other tool (`not_configured` when the header is absent, `invalid_argument` when the region/base URL header is malformed) — never an unhandled exception.
- **AC7** — Given IT Glue rejects the request (409/422 duplicate type name or invalid `kind`, 401/403, 429, or 5xx), when `itglue_create_flexible_asset_type` is called, then the error is mapped through the existing `code`/`message`/`retryable` envelope exactly as it is for every other tool, with the retryable ones retried with backoff, and no field's `default_value` ever appears in the error message.
- **AC8** — Given the MCP's `tools/list` is queried, when `itglue_create_flexible_asset_type` is registered, then it is **not** read-only (`readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: false` — matching `CREATE` annotations), has no `agent_id` parameter, is listed in `README.md`'s Tools table, and no existing tool's name or parameters change.

### Open questions

- **[已假设] Attribute casing mismatch, not blocking.** The ticket's own Rewst-sourced example uses `"type": "flexible-asset-fields"` (hyphenated) and `"show_in_list": true` (snake_case) at the field level, while every other write endpoint already proven in this repo uses kebab-case attributes (`organization-id`, `flexible-asset-type-id`, confirmed in `tests/test_flexible_assets.py:61-72`) and this repo's own `api.attributes()` helper dasherizes automatically. The design proceeds on the assumption that IT Glue's JSON:API, like the rest of its resources, expects **kebab-case attribute keys** and a resource `type` of `flexible_asset_fields` (underscored, matching the `/flexible_asset_types` and `/flexible_assets` naming already used elsewhere in this same connector) — i.e. it treats Rewst's example as "a body that happened to work," not as proof of IT Glue's canonical casing, and reuses the one, already-tested JSON:API builder rather than hand-rolling a second casing convention for one tool. If this assumption is wrong, IT Glue returns a 422 (already mapped to the standard `invalid_argument` envelope — a loud, visible failure, not a silent one), and the fix is a one-line casing change local to this tool. Non-blocking: wrong casing fails safely and visibly.
- **[不阻塞] Full `kind` enum not available.** The ticket lists six example kinds (Text/Textbox/Password/Tag/Checkbox/Date/Number) explicitly as examples ("等"/"etc."), and the automated fetch of IT Glue's public API docs did not return the complete enum (see Current state). The design does not validate `kind` locally — same convention this connector already uses for other vendor-defined enums it does not want to duplicate and risk drifting from (e.g. `sort` values are forwarded unvalidated, `docs/tickets/PRD-21586.md` AC3). IT Glue rejects an invalid `kind` with a mapped `invalid_argument` error (AC7). Default by not validating; can be tightened later if a wrong `kind` turns out to be a common caller mistake.
- **[不阻塞] No tool to read a type's fields back.** This connector has no "list the fields of a flexible asset type" tool (distinct from `list_flexible_asset_types`, which lists types, not a type's fields). If IT Glue's create response includes bare `{id, type}` refs for the created fields under `relationships.flexible-asset-fields.data`, the new tool surfaces them as `fields: [{"id": ...}, ...]` in its own response (Tech design §5); getting a field's full attributes back afterward is out of scope for this ticket (the ticket only asks for creation) and is not something either Rewst flow this ticket replaces needs. Flagged as a possible follow-up, not filed as a separate ticket by this design.
- **No live IT Glue test account is available to DEV01.** Per `references/mcp-track.md` §3 ("completion standard"), missing a vendor test account does not block design or development; cases that need one are marked accordingly in the test cases below.

## Tech design

### Conclusion

Add one new write tool, `itglue_create_flexible_asset_type`, in the existing `src/itglue_mcp/tools/flexible_assets.py` module (no new file — it is the fifth operation on the resource this module already owns). It is `POST /flexible_asset_types` with an optional nested `relationships.flexible-asset-fields` block. The one piece of new, reusable machinery is a `relationships` parameter added to `api.attributes()` so this (and any future tool needing a nested-create) can build a compound JSON:API document without a second body-building path.

### Option analysis

- **Chosen — add `itglue_create_flexible_asset_type` to the existing `tools/flexible_assets.py` module; extend `api.attributes()` with an optional `relationships` parameter.** One new tool in the module that already owns this resource area (matches the repo's "one module per resource" convention, `README.md:169`); one small, backward-compatible extension to the one JSON:API body builder every write tool already goes through, instead of a second, parallel body-building function that would only exist for this one tool.
- **Rejected — build the compound request body ad hoc inside the new tool, without touching `api.py`.** Would duplicate `api.attributes()`'s dasherizing/`None`-dropping logic a second time for one call site, and the next tool that needs a nested-create (there will likely be one, since several IT Glue resources support compound documents) would face the same choice again. Extending the shared helper is the DRY option and costs one optional parameter.
- **Rejected — a new `tools/flexible_asset_types.py` module.** Over-splits one resource (`flexible_asset_types` vs `flexible_assets`) that the repo already treats as one area in its own Tools table row ("Flexible assets", `README.md:107`) and one module; `list_flexible_asset_types` already lives in `flexible_assets.py` for the same reason.
- **Rejected — generic "create any IT Glue resource with relationships" tool.** Over-generalizes for one new capability (YAGNI); breaks the connector's explicit-name-and-schema convention that keeps the agent-facing contract discoverable and typed, same conclusion PRD-21586's tech design reached for a generic list tool.

### Data & API contract

Request (MCP tool call):

```
itglue_create_flexible_asset_type(
  name: string,                 // required
  enabled?: boolean,
  description?: string,
  icon?: string,                // IT Glue icon name
  fields?: [{
    name: string,                // required per field
    kind: string,                 // required per field; not locally validated (see Open questions)
    order?: integer,
    required?: boolean,
    show_in_list?: boolean,
    use_for_title?: boolean,
    tag_type?: string,
    hint?: string,
    default_value?: any           // masked from error messages/logs if present
  }]
) -> string (JSON)
```

Upstream call: `POST /flexible_asset_types` built via `api.attributes("flexible_asset_types", {name, enabled, description, icon}, relationships={"flexible-asset-fields": [...]})` when `fields` is non-empty, otherwise `relationships=None` (no key in the body at all — AC4):

```json
{
  "data": {
    "type": "flexible_asset_types",
    "attributes": {
      "name": "BitLocker (Rewst)",
      "enabled": true,
      "description": "Store BitLocker keys here"
    },
    "relationships": {
      "flexible-asset-fields": {
        "data": [
          {
            "type": "flexible_asset_fields",
            "attributes": {
              "kind": "Textbox",
              "name": "BitLocker Keys",
              "order": 0,
              "show-in-list": true
            }
          }
        ]
      }
    }
  }
}
```

(Casing per the Open-questions assumption: kebab-case attributes, `type: flexible_asset_fields` — not the ticket's literal Rewst example, which the design treats as "a body that happened to work" rather than canonical.)

Response (success):

```json
{
  "id": "789",
  "name": "BitLocker (Rewst)",
  "enabled": true,
  "description": "Store BitLocker keys here",
  "icon": null,
  "fields": [{"id": "456"}]
}
```

`fields` is only present when the upstream response's `data.relationships["flexible-asset-fields"].data` is non-empty; it carries bare `{"id": ...}` refs (IT Glue's compound-create response is not expected to expand full field attributes without `?include=`, matching JSON:API convention) — see Open questions for why reading full field attributes back is out of scope.

Response (error), same envelope every tool returns on failure: `{"error": {"code": "...", "message": "...", "retryable": false}}`, `code` one of `not_configured`, `unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error` (`src/itglue_mcp/api.py:39-57`). A field's `default_value` is masked from `message` the same way a `traits` value is (`run(..., secrets=[...])`).

**Backward compatibility:** purely additive. No existing tool's name, parameters or response shape changes; `api.attributes()`'s new parameter defaults to `None` and every existing call site is unaffected (unit-tested by re-running the existing `test_create_flexible_asset_happy_path` / `test_update_flexible_asset_*` tests unmodified). `tests/fixtures/tools_baseline.json` is widened, never narrowed.

### Key flow / sequence

1. Agent Platform / gateway calls `itglue_create_flexible_asset_type` over MCP with the tenant's `X-ITGlue-API-Key` (+ optional region/base URL) headers, unchanged from every other call to this server.
2. `CredentialMiddleware` extracts and validates the headers (unchanged).
3. The new tool handler validates each `fields` entry locally (`name`+`kind` present) and raises `ToolInputError` before any HTTP call if not (AC5).
4. The handler builds the request body via the extended `api.attributes("flexible_asset_types", type_values, relationships=...)` and calls `POST /flexible_asset_types` through the per-request `ITGlueClient`.
5. `api.item()` flattens `data.attributes`; the handler separately reads `data.relationships["flexible-asset-fields"].data` (if present) to attach bare field-id refs.
6. `run()` wraps any upstream error into the standard error envelope, masking `default_value`s; nothing here is new.

### Non-functional

- **Idempotency & concurrency:** `POST /flexible_asset_types` is not idempotent (two identical calls create two types, or the second 409s on a duplicate name per IT Glue's own uniqueness rule) — this is inherent to the vendor's "create" semantics, same as `create_flexible_asset` and `create_location` today; no new concurrency concern this connector doesn't already have for every other create tool.
- **Security:** no change to the credential model — API key stays header-only, never persisted, never logged (`src/itglue_mcp/tools/_common.py:80-106`). A field's `default_value` is the one new potentially-sensitive value this tool introduces (a `Password`-kind field could carry a default secret); masked via the same `run(..., secrets=[...])` path `_trait_secrets` already uses, extended to cover `fields[*].default_value`.
- **Multi-tenant isolation:** unaffected. One `ITGlueClient` is created per request, scoped to that request's own API key (`src/itglue_mcp/api.py:92-99`); flexible asset types are account-wide (not organization-scoped, same as `list_flexible_asset_types`'s existing `organization_id` parameter being "accepted for compatibility ... ignored", `:40-43`), so there is no organization-level isolation concern specific to this tool — only the usual "each tenant's API key only ever sees that tenant's IT Glue account" guarantee, unchanged.
- **Performance:** single request, no pagination; bounded by the existing retry/backoff logic in `api.py:107-146` (3000 requests / 5 minutes IT Glue rate limit, already handled generically). A `fields` list with many entries is still one HTTP request (IT Glue's compound-document create), not N requests.
- **Observability:** errors flow through the same `log.exception` / structured-envelope path as every other tool (`src/itglue_mcp/tools/_common.py:99-106`); nothing new to add.

### Rollout & rollback

Purely additive tool — no feature flag needed; adding a tool cannot break an existing caller, and the `api.attributes()` extension is backward compatible by construction (new optional parameter, default preserves old behaviour). Ships via the standard MCP flow: merge to `main`, `mcppub publish` re-runs the full test suite on `main` before deploying, then redeploys to INT. Rollback is a revert of the merge commit followed by a re-publish — no data or schema to roll back (this repo is stateless).

### Test strategy

- **Unit (new), `tests/test_flexible_assets.py`:** name-only create (AC1); full-attributes create asserting unset optionals are omitted, not `null` (AC2); create-with-fields asserting the exact `relationships.flexible-asset-fields.data[]` body, including the kebab-case/`flexible_asset_fields` casing decision (AC3); omitted/empty `fields` asserting **no** `relationships` key at all in the sent body (AC4); a field missing `name` or `kind` raising before any `respx` route is hit (AC5); error-does-not-leak test mirroring `test_create_flexible_asset_error_does_not_leak_trait_values` but for a field's `default_value` (AC7).
- **Contract (modify), `tests/fixtures/tools_baseline.json` + `tests/test_tools.py`:** add the new tool's baseline entry; this automatically extends `test_tool_names_match_baseline`, `test_parameters_are_backward_compatible`, `test_descriptions_are_concise` and `test_no_agent_id_parameter` (AC8) — no new test code needed beyond the fixture entry. `test_annotations` is extended with one assertion that `itglue_create_flexible_asset_type`'s `readOnlyHint` is `False` (it is a write tool, unlike the four read-only tools that test currently names, `tests/test_tools.py:34-39`).
- **Regression, `tests/test_middleware.py`:** bump the two hardcoded `37` counts to `38` (mechanical; the pre-existing test itself does not need new logic).
- **`api.py` unit test (new or extended):** one direct test of `attributes()` with `relationships=None` (today's output, unchanged byte-for-byte) and one with a `relationships` dict, asserting the exact nested shape — this is the one piece of genuinely new, reusable machinery and deserves its own direct test, not only indirect coverage through the tool test.
- **Errors/credentials (inherited):** AC6 is already covered generically by `test_missing_credentials_envelope` (`tests/test_handlers.py`), which exercises the shared `run()`/`ITGlueClient` path every tool goes through; no per-tool duplicate is needed.
