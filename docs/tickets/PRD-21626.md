## Requirement understanding

One line: Add an itglue_flexible_asset_attachments tool to the IT Glue MCP connector that can add and remove (POST/DELETE) attachment relationships on a flexible asset, so the Rewst it_glue.generic_request call used in EMD Networking Services' "ITG: Upsert Flexible Asset" sub-flow can be rebuilt as an MSPbots agent tool.

This ticket is item 63/N of the Rewst -> MSPbots migration gap register (`mspbots-gap-register.xlsx`). It targets one Rewst account (EMD Networking Services) whose "ITG: Upsert Flexible Asset" sub-flow (evidence tier B, run count over the trailing 365 days) calls IT Glue's generic request action against `POST`/`DELETE https://api.itglue.com/flexible_assets/{id}/relationships/attachments` to attach or detach a file on a flexible asset. The gap register's stated current-state note ("the first-tenant connector has only `list_flexible_asset_types` / `search_flexible_assets`, no create/update/read-by-id, no `create_attachment`/`list_attachments` verified against flexible assets") is **stale** — see Current state below; it does not match what is in the repo today.

## Product design

### Goals / Non-goals

**Goals**

- Add one new tool, `delete_attachment`, that removes an attachment relationship from an IT Glue record (any of the eleven resource types `create_attachment`/`list_attachments` already support, including `flexible_assets`), closing the only capability gap the ticket actually has — the detach direction.
- Keep its shape consistent with the sibling tools already in this module (`create_attachment`, `list_attachments`): same `resource_type`/`resource_id` parameters, same module, same error and annotation conventions.

**Non-goals**

- No new `itglue_flexible_asset_attachments`-named, flexible-asset-only tool. The ticket's literal tool name describes one resource type, but the capability it asks for (attach/detach a file) is already modeled generically in this connector across eleven resource types including `flexible_assets` — see Option analysis for why a flexible-asset-specific tool would be the wrong shape.
- No change to `create_attachment` or `list_attachments` — the attach/list directions already work against `flexible_assets` and need no code change.
- No change to any other existing tool's name, parameters, or behaviour.
- No UI change — this is a connector-level (MCP) change, not an Agent Platform page.
- No new connector and no gateway change — the repo already exists and this is an in-repo addition.

### Acceptance criteria AC1..ACn

- **AC1** — Given valid IT Glue credentials and a valid `resource_type` (one of the eleven types `create_attachment`/`list_attachments` already support, including `flexible_assets`), `resource_id` and `attachment_id`, when `delete_attachment` is called, then it sends `DELETE /{resource_type}/{resource_id}/relationships/attachments` with the attachment id in the request body and returns `{"id": "<attachment_id>", "deleted": true}` on success.
- **AC2** — Given the same successful call with `resource_type="flexible_assets"`, when `delete_attachment` is called, then the detach succeeds the same way as for any other resource type — this is the concrete capability the ticket (EMD Networking Services' "ITG: Upsert Flexible Asset" sub-flow) needs.
- **AC3** — Given an `attachment_id` that does not exist (or was already deleted), when `delete_attachment` is called, then IT Glue's error response is mapped through the existing structured error envelope (`not_found` or whatever status IT Glue actually returns), never an unhandled exception.
- **AC4** — Given missing or invalid IT Glue credentials, when `delete_attachment` is called, then it returns the same structured error envelope as every other tool (`not_configured` when the header is absent, `invalid_argument` when the region/base URL header is malformed).
- **AC5** — Given IT Glue returns an error (401/403, 404, 422, 429, or 5xx), when `delete_attachment` is called, then the error is mapped through the existing `code` / `message` / `retryable` envelope exactly as it is for every other tool, with the retryable ones retried with backoff.
- **AC6** — Given the MCP's `tools/list` is queried, when `delete_attachment` is registered, then it is destructive (`destructiveHint: true`, `readOnlyHint: false`), has no `agent_id` parameter, is listed in `README.md`'s Tools table, and does not remove or change any existing tool's name or parameters.

### Open questions

- **Idempotency of a repeated delete, not blocking.** IT Glue's public docs do not state whether deleting an already-detached attachment relationship returns a 404/422 or a no-op success. Proceeding on the assumption that it behaves like `delete_document`'s precedent in this repo (not idempotent; a second call is expected to surface IT Glue's own error, mapped through the standard envelope per AC3) rather than inventing idempotent "already deleted" handling the vendor API does not document. If IT Glue's actual behaviour differs, the dev leg's self-test against a real or documented response will show it; this does not change the tool's contract either way (AC3 covers both as a mapped error / a `deleted: true` success).
- **No live IT Glue test account is available to DEV01.** Per `references/mcp-track.md` §3 ("completion standard"), missing a vendor test account does not block design or development; cases that need one are marked accordingly in the test cases below.

## Tech design

### Conclusion

Add one new tool, `delete_attachment`, to the existing `src/itglue_mcp/tools/attachments.py` module (not a new module, and not a flexible-asset-specific tool) — a thin `DELETE` counterpart to the `create_attachment`/`list_attachments` pair already in that file, reusing the same `ResourceType` literal, the same `seg()`/`run()` helpers, and the `DESTRUCTIVE` annotation already used by `delete_document`. This closes the only real gap (detach) the ticket has; the attach (POST) and list directions need no change because they already support `flexible_assets`.

### Where the current implementation lives

### Option analysis

- **Chosen — add `delete_attachment` to the existing `attachments.py` module, generic across all eleven `ResourceType` values.** One function, reuses the module's existing `ResourceType` literal and its two sibling tools' shape exactly. An agent that already knows `create_attachment`/`list_attachments` needs no new concept to use `delete_attachment` on any resource type, including `flexible_assets`.
- **Rejected — a flexible-asset-only tool literally named `itglue_flexible_asset_attachments`, as the ticket's tool-name field states.** This would duplicate logic the module already generalizes (attach/list already work identically across eleven resource types, not just `flexible_assets`), introduce an inconsistent one-off next to two generic siblings, and give agents two different ways to manage attachments depending on which resource type they're touching. The ticket's literal tool name is Rewst/gap-register bookkeeping (it names the sub-flow's primary resource), not an architectural requirement — the actual requirement, "add/remove attachment relationships," is exactly what `create_attachment`/`list_attachments`/`delete_attachment` already model together. Following the repo's own generic shape is the "reuse before build" call here, per the 2026-10-28 code-quality rule.
- **Rejected — a generic "modify any IT Glue relationship" tool.** Over-generalizes for one new capability (YAGNI); attachments are the only relationship type this connector exposes write access to, so a relationship-agnostic tool would need per-relationship-type field handling anyway with no present second use case.

### Data & API contract

Request (MCP tool call):

```
delete_attachment(
  resource_type: "checklists" | "checklist_templates" | "configurations" | "contacts" |
                 "documents" | "domains" | "flexible_assets" | "locations" | "passwords" |
                 "ssl_certificates" | "tickets",
  resource_id: int,       // ID of the record the attachment is on
  attachment_id: int      // ID of the attachment relationship to remove
) -> string (JSON)
```

Upstream call: `DELETE /{resource_type}/{resource_id}/relationships/attachments` with body `{"data": [{"type": "attachments", "attributes": {"id": <attachment_id>}}]}` — the same `type` + `attributes.id` shape this repo's own `delete_document` already uses, and the shape IT Glue's public API documentation specifies for this relationship-delete endpoint (fetched 2026-10-31).

Response (success):

```json
{"id": "987", "deleted": true}
```

Response (error), same envelope every tool returns on failure: `{"error": {"code": "...", "message": "...", "retryable": false}}`, `code` one of `not_configured`, `unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error` (`src/itglue_mcp/api.py:39-57`).

**Backward compatibility:** purely additive. No existing tool's name, parameters or response shape changes. `tests/fixtures/tools_baseline.json` is widened (a new entry added), never narrowed — `test_tool_names_match_baseline` (`tests/test_tools.py:14-17`) requires the baseline and the live tool set to match exactly, so the baseline update ships in the same commit as the tool.

### Key flow / sequence

1. Agent Platform / gateway calls `delete_attachment` over MCP with the tenant's `X-ITGlue-API-Key` (+ optional region/base URL) headers, unchanged from every other call to this server.
2. `CredentialMiddleware` extracts and validates the headers (unchanged).
3. The new tool handler validates `resource_id`/`attachment_id` are numeric (`seg()`), builds the JSON:API delete body, and calls `DELETE /{resource_type}/{resource_id}/relationships/attachments` through the per-request `ITGlueClient`.
4. On success (IT Glue returns 204/empty body, per `api.py:146-147`'s "no content -> return None" handling), the handler returns `{"id": ..., "deleted": True}`.
5. `run()` wraps any upstream error into the standard error envelope; nothing here is new.

### Non-functional

- **Security:** no change to the credential model — API key stays header-only, never persisted, never logged (`src/itglue_mcp/tools/_common.py:80-106`). `attachment_id`/`resource_id` are validated as numeric via `seg()` before being placed in the URL path, same guard every other ID-taking tool uses.
- **Multi-tenant isolation:** unaffected. One `ITGlueClient` is created per request, scoped to that request's own API key (`src/itglue_mcp/api.py:92-99`); a tenant can only ever delete attachments on records its own key can reach. No new state is introduced that could leak across tenants or requests.
- **Performance:** a single DELETE call per invocation, bounded by the existing retry/backoff logic in `api.py:107-146` (3000 requests / 5 minutes IT Glue rate limit, already handled generically). No paging involved.
- **Observability:** errors flow through the same `log.exception` / structured-envelope path as every other tool (`src/itglue_mcp/tools/_common.py:99-106`); nothing new to add.
- **Destructive-action posture:** `delete_attachment` is marked `destructiveHint: true` / `readOnlyHint: false`, matching `delete_document`'s precedent, so platform-side agent policy (confirm-before-destructive-call, if any) applies to it the same way.

### Rollout & rollback

Purely additive tool — no feature flag needed; adding a tool cannot break an existing caller. Ships via the standard MCP flow: merge to `main`, `mcppub publish` re-runs the full test suite on `main` before deploying, then redeploys to INT. Rollback is a revert of the merge commit followed by a re-publish — no data or schema to roll back (this repo is stateless).

### Test strategy

- **Unit (new), `tests/test_handlers.py`:** one test asserting the DELETE request body shape (`{"data": [{"type": "attachments", "attributes": {"id": <id>}}]}`) and path (`/{resource_type}/{resource_id}/relationships/attachments`) for a generic resource type; one test specifically with `resource_type="flexible_assets"` asserting the same shape against the flexible-assets path (AC2, the ticket's concrete need); one test asserting a 404 from IT Glue on delete is mapped to `{"error": {"code": "not_found", ...}}` (AC3).
- **Contract (modify), `tests/fixtures/tools_baseline.json` + `tests/test_tools.py`:** add the new tool's baseline entry; this automatically extends `test_tool_names_match_baseline`, `test_parameters_are_backward_compatible`, `test_annotations` (expect `destructiveHint: true`, `readOnlyHint: false`) and `test_no_agent_id_parameter` to cover it (AC6) — no new test code needed beyond the fixture entry.
- **Middleware (modify), `tests/test_middleware.py`:** bump the two hardcoded tool-count assertions from `37` to `38`.
- **Errors/credentials (inherited):** AC4 and AC5 (other than the not-found case, which gets its own test above) are already covered generically by `test_missing_credentials_envelope` and `test_error_mapping` (`tests/test_handlers.py`), which exercise the shared `run()`/`ITGlueClient` path every tool goes through; no per-tool duplicate is needed for those, since nothing in the new tool changes that path. Invalid `resource_type` values are rejected by the MCP input-schema layer (the `Literal` type) before the handler ever runs, the same inherited behaviour every other `resource_type`-taking tool already has — no new test needed.
- **No real IT Glue account needed** for any of the above — all tests mock the HTTP layer with `respx`, same as every existing test in this repo. The INT publish step re-runs this suite before deploying, which is the closest thing to an integration check this repo has.
