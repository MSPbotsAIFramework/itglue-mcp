## Requirement understanding

One line: Add a new tool to the IT Glue MCP connector that lists the users in an IT Glue account (id, name, email, role, My Glue flag, last sign-in), so the license-counting workflow that today runs on Rewst (`it_glue.list_accounts_users`) can be rebuilt as an MSPbots agent.

This ticket is item 18/56 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It targets two Rewst accounts (Ginko IT, EMD Networking Services) that both call IT Glue's "list account users" action — one in a billing/license-count sub-flow, the other in a documentation flow — and the gap is that the MSPbots IT Glue connector has no tool that reads the account's user directory. The closest existing tool, `search_user_metrics`, reads per-user *activity* counts (`/user_metrics`), not the user directory (`/users`) itself, so it cannot substitute.

## Current state (every claim carries path:line)

- `MSPbotsAIFramework/itglue-mcp` is the only IT Glue MCP in MSPbotsAIFramework (`mbp.py mcplock info --repo itglue-mcp` → default branch `main`); Code Repo was empty and has been filled with this repo (see stub).
- The server registers nine tool areas: Organizations, Configurations, Locations, Passwords, Documents, Document sections, Attachments, Flexible assets, Activity, Diagnostics (`README.md:98-109`). None of them reads `/users` — `search_user_metrics` is the only tool that touches user-related data, and it calls `/user_metrics`, not `/users` (`src/itglue_mcp/tools/user_metrics.py:76`).
- Every list-style tool follows the same shape: a `register(mcp, settings)` function registers one or more `@mcp.tool`s; filters are optional keyword args forwarded as `filter[...]` query params; paging is handled by the shared `locate()` / `api.page()` helpers (`src/itglue_mcp/tools/organizations.py:15-52`, `src/itglue_mcp/tools/locations.py:27-73`, `src/itglue_mcp/tools/_common.py:45-59`, `src/itglue_mcp/api.py:183-220`).
- Credentials are read once per request from `X-ITGlue-API-Key` (+ optional `X-ITGlue-Region` / `X-ITGlue-Base-URL`) by `CredentialMiddleware`, then handed to one `ITGlueClient` per call inside `run()`; nothing is cached across requests (`src/itglue_mcp/tools/_common.py:80-106`, `src/itglue_mcp/api.py:89-99`). Errors from the upstream API are mapped to one of `not_configured` / `invalid_argument` / `unauthorized` / `not_found` / `rate_limited` / `upstream_error` (`src/itglue_mcp/api.py:39-57`).
- `tests/fixtures/tools_baseline.json` plus `tests/test_tools.py:14-17` assert the exact set of tool names and that no tool loses a parameter or gains a new required one — this is the backward-compatibility gate every tool addition must satisfy.
- `tests/test_paging_offset.py:40-48` keeps a `LISTS` table of every list-style tool and runs one shared "cut pages are walked by `next_offset` without skipping or duplicating records" test against all of them.
- Per the public IT Glue API documentation (https://api.itglue.com/developer/, fetched 2026-10-30), `GET /users` supports `filter[id]`, `filter[name]` (exact match only), `filter[email]`, `filter[role_name]`, `filter[salesforce_id]`, and `sort` on `name`, `email`, `reputation`, `id`, `created_at`, `updated_at` (prefix `-` for descending). Returned attributes are `first-name`, `last-name`, `email`, `role-name`, `avatar`, `reputation`, `invitation-sent-at`, `invitation-accepted-at`, `current-sign-in-at`, `current-sign-in-ip`, `last-sign-in-at`, `last-sign-in-ip`, `my-glue`, `my-glue-account-id`. Note this does not match the ticket's literal field list (it says `attributes.name`; IT Glue actually splits `first-name` / `last-name`) — see Open questions.

## Product design

### Goals / Non-goals

**Goals**

- Add one new read-only tool, `itglue_list_account_users`, that lists the users of the authenticated IT Glue account with enough fields (name, email, role, My Glue flag, last sign-in) to support license-count and audit use cases, matching the capability the ticket asks for.
- Keep it filterable and sortable the same way every other list tool in this connector is (name / email / role, optional sort, paging), so agents that already know this connector's conventions can use it without new concepts.

**Non-goals**

- No write operations on users (create/update/deactivate) — the ticket and the Rewst flows it replaces are both read-only.
- No change to any existing tool's name, parameters, or behaviour.
- No UI change — this is a connector-level (MCP) change, not an Agent Platform page.
- No new connector and no gateway change — the repo already exists and this is an in-repo addition.

### Acceptance criteria AC1..ACn

- **AC1** — Given valid IT Glue credentials and no filters, when `itglue_list_account_users` is called, then it returns the connector's standard list envelope (`items`, `count`, `page_number`, `page_size`, `has_more`[, `total_count`, `offset`, `next_offset`]) where each item carries at least `id`, `first_name`, `last_name`, `email`, `role_name`, `my_glue` and `last_sign_in_at`.
- **AC2** — Given `name`, `email` and/or `role_name` are passed, when `itglue_list_account_users` is called, then only users matching those filters are returned (each forwarded as IT Glue's `filter[name]` / `filter[email]` / `filter[role_name]`; `name` is an exact match per IT Glue's API, documented as a behaviour note).
- **AC3** — Given a `sort` value (one of `name`, `email`, `reputation`, `id`, `created_at`, `updated_at`, optionally prefixed with `-` for descending), when `itglue_list_account_users` is called, then the `sort` query parameter is forwarded unchanged, matching every other list tool's sort parameter.
- **AC4** — Given the account has more users than fit on one page, when a caller walks the result with `next_offset` (or `page_number`), then every user is returned exactly once, none are skipped or duplicated, and a cut page continues exactly where the previous one stopped — the same guarantee already enforced for every other list tool.
- **AC5** — Given missing or invalid IT Glue credentials, when `itglue_list_account_users` is called, then it returns the same structured error envelope as every other tool (`not_configured` when the header is absent, `invalid_argument` when the region/base URL header is malformed) — never an unhandled exception.
- **AC6** — Given IT Glue returns an error (401/403, 404, 422, 429, or 5xx), when `itglue_list_account_users` is called, then the error is mapped through the existing `code` / `message` / `retryable` envelope exactly as it is for every other tool, with the retryable ones retried with backoff.
- **AC7** — Given the MCP's `tools/list` is queried, when `itglue_list_account_users` is registered, then it is read-only (`readOnlyHint: true`), has no `agent_id` parameter, is listed in `README.md`'s Tools table, and does not remove or change any existing tool's name or parameters.

### Open questions

- **Field name mismatch, not blocking.** The ticket's "returned fields" list says `attributes.name`; IT Glue's real `/users` response has `first-name` and `last-name` instead (confirmed against the public API docs). Proceeding on the assumption that the tool should expose IT Glue's actual attributes as-is (`first_name`, `last_name`, ...) rather than inventing a combined `name` field IT Glue doesn't provide — consistent with how every other tool in this connector flattens attributes verbatim (`src/itglue_mcp/api.py:163-173`). If the caller specifically needs a single combined display name, that is a trivial follow-up, not a reason to hold this ticket.
- **No live IT Glue test account is available to DEV01.** Per `references/mcp-track.md` §3 ("completion standard"), missing a vendor test account does not block design or development; cases that need one are marked accordingly in the test cases below.

## Tech design

### Conclusion

Add one new read-only tool, `itglue_list_account_users`, in a new module `src/itglue_mcp/tools/users.py`, registered in `src/itglue_mcp/server.py` next to the existing tool modules. It is a thin, filterable, paginated wrapper around `GET /users`, built entirely from the helpers every other list tool already uses (`api.page`, `api.flatten`, `tools/_common.py`'s `run`/`locate`/`READ`). No architectural change, no new dependency, no change to any existing tool.

### Where the current implementation lives

- `src/itglue_mcp/server.py:15-24,51-61` — tool module registration tuple (import list + `create_mcp` loop).
- `src/itglue_mcp/tools/organizations.py:15-52` — the closest existing pattern: a simple, filterable, paginated `search_*` tool with no path parameter.
- `src/itglue_mcp/tools/locations.py:27-73` — a second example of the same shape, including a `sort` parameter.
- `src/itglue_mcp/tools/_common.py:22-59,80-106` — `READ` annotations, `PageSize`/`PageNumber`/`Offset` types, `locate()`, `run()`.
- `src/itglue_mcp/api.py:147-149,183-220` — `ITGlueClient.get`, `page()`, `flatten()`.
- `README.md:96-136` — Tools table and behaviour notes.
- `tests/fixtures/tools_baseline.json`, `tests/test_tools.py:14-17` — backward-compatibility contract test.
- `tests/test_paging_offset.py:40-48` — shared pagination-contract test table (`LISTS`).
- `tests/test_handlers.py:21-34,41-65` — pattern for a tool's filter-forwarding test and the shared `test_missing_credentials_envelope` / `test_error_mapping` tests (these already exercise the shared `run()` path and do not need a per-tool copy).

### Option analysis

- **Chosen — new module `tools/users.py`, same shape as `organizations.py`.** One file, one tool, reuses every existing helper. Matches the repo's own convention of "one module per resource area" (`README.md:169`).
- **Rejected — add it to `tools/user_metrics.py`.** `/user_metrics` (activity log) and `/users` (user directory) are different IT Glue resources with different semantics; folding them into one module would make that module's docstring ("User activity metrics") wrong and mix two unrelated concerns in one file, the opposite of what the rest of the repo does.
- **Rejected — a generic "list any IT Glue resource" tool.** Over-generalizes for one new capability (YAGNI); every other tool in this connector has an explicit name and schema so the agent-facing contract stays discoverable and typed. A generic resource tool would need per-resource field handling anyway, which is exactly what the one-module-per-resource pattern already gives for free.

### Reuse & cleanup

- **Reuses:** `api.ITGlueClient.get`, `api.page`/`api.flatten`, `tools/_common.py`'s `READ`, `PageSize`/`PageNumber`/`Offset`, `locate()`, `run()`. No new third-party dependency.
- **New tool signature:** `itglue_list_account_users(name=None, email=None, role_name=None, sort=None, page_size=None, page_number=None, offset=None) -> str`. All-optional keyword arguments, same shape as `search_organizations` and `search_locations`, so future filters (e.g. `salesforce_id`, which IT Glue also supports) can be added later without breaking existing callers.
- **Decision — no field dropping.** Unlike `passwords.py`'s `SECRET_FIELDS` (actual secrets) or `documents.py`'s `{"content"}` (large bodies), nothing in the `/users` response is a secret or oversized; the tool flattens and returns every attribute IT Glue gives, same as `organizations.py` and `locations.py` do. This includes `current_sign_in_ip` / `last_sign_in_ip`; it is informational, already gated by the same per-tenant API key and RBAC as every other tool's output, and dropping it would be an undocumented, inconsistent special case for no stated requirement.
- **In-scope cleanup:** none found — the touched files (`server.py`, `README.md`, the new module) have no unused code or stale comments to remove.
- **Follow-ups (out of scope, not filed as separate tickets by this design):** none identified; this is a pure addition.

### Data & API contract

Request (MCP tool call):

```
itglue_list_account_users(
  name?: string,        // forwarded as filter[name] (exact match, see behaviour note)
  email?: string,       // forwarded as filter[email]
  role_name?: string,   // forwarded as filter[role_name]
  sort?: string,        // one of name|email|reputation|id|created_at|updated_at, "-" prefix = descending
  page_size?: int,      // default 50, max 200
  page_number?: int,    // default 1
  offset?: int          // overrides page_number; pass next_offset from a previous call
) -> string (JSON)
```

Upstream call: `GET /users` with `filter[name]`, `filter[email]`, `filter[role_name]`, `sort`, `page[size]`, `page[number]` — unset filters are omitted, same as every other tool (`src/itglue_mcp/api.py:117`).

Response (success), same envelope every list tool returns:

```json
{
  "items": [
    {
      "id": "123",
      "first_name": "Jane",
      "last_name": "Doe",
      "email": "jane@example.com",
      "role_name": "Administrator",
      "avatar": null,
      "reputation": 420,
      "invitation_sent_at": "2025-01-01T00:00:00Z",
      "invitation_accepted_at": "2025-01-02T00:00:00Z",
      "current_sign_in_at": "2026-10-29T10:00:00Z",
      "current_sign_in_ip": "203.0.113.4",
      "last_sign_in_at": "2026-10-28T09:00:00Z",
      "last_sign_in_ip": "203.0.113.5",
      "my_glue": false,
      "my_glue_account_id": null
    }
  ],
  "count": 1,
  "page_number": 1,
  "page_size": 50,
  "has_more": false,
  "total_count": 1,
  "offset": 0
}
```

Response (error), same envelope every tool returns on failure: `{"error": {"code": "...", "message": "...", "retryable": false}}`, `code` one of `not_configured`, `unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error` (`src/itglue_mcp/api.py:39-57`).

**Backward compatibility:** purely additive. No existing tool's name, parameters or response shape changes. `tests/fixtures/tools_baseline.json` is widened (a new entry added), never narrowed — `test_tool_names_match_baseline` (`tests/test_tools.py:14-17`) requires the baseline and the live tool set to match exactly, so the baseline update ships in the same commit as the tool.

### Key flow / sequence

1. Agent Platform / gateway calls `itglue_list_account_users` over MCP with the tenant's `X-ITGlue-API-Key` (+ optional region/base URL) headers, unchanged from every other call to this server.
2. `CredentialMiddleware` extracts and validates the headers (unchanged).
3. The new tool handler builds `filter[...]`/`sort` query params via the shared `locate()` helper and calls `GET /users` through the per-request `ITGlueClient`.
4. `api.page()` flattens the JSON:API response into the standard list envelope.
5. `run()` wraps any upstream error into the standard error envelope; nothing here is new.

### Non-functional

- **Security:** no change to the credential model — API key stays header-only, never persisted, never logged (`src/itglue_mcp/tools/_common.py:80-106`). The `/users` resource has no secret fields, so (unlike `passwords.py`) no `drop` set is needed; see the Reuse & cleanup decision above.
- **Multi-tenant isolation:** unaffected. One `ITGlueClient` is created per request, scoped to that request's own API key (`src/itglue_mcp/api.py:92-99`); a tenant can only ever see the users of the IT Glue account its own key belongs to. No new state is introduced that could leak across tenants or requests.
- **Performance:** same `page_size` default (50) and cap (200) as every other list tool; this is a thin passthrough bounded by the existing retry/backoff logic in `api.py:107-146` (3000 requests / 5 minutes IT Glue rate limit, already handled generically).
- **Observability:** errors flow through the same `log.exception` / structured-envelope path as every other tool (`src/itglue_mcp/tools/_common.py:99-106`); nothing new to add.

### Rollout & rollback

Purely additive tool — no feature flag needed; adding a tool cannot break an existing caller. Ships via the standard MCP flow: merge to `main`, `mcppub publish` re-runs the full test suite on `main` before deploying, then redeploys to INT. Rollback is a revert of the merge commit followed by a re-publish — no data or schema to roll back (this repo is stateless).

### Test strategy

- **Unit (new), `tests/test_handlers.py`:** one test asserting `itglue_list_account_users` returns the list envelope with the fields listed in AC1, built from a mocked `GET /users` response (same `respx` pattern as `test_search_organizations_paging_and_filters`); one test asserting `name`/`email`/`role_name` are forwarded as `filter[...]` (AC2) and that `sort` (including a `-`-prefixed value) is forwarded unchanged (AC3).
- **Contract (modify), `tests/fixtures/tools_baseline.json` + `tests/test_tools.py`:** add the new tool's baseline entry; this automatically extends `test_tool_names_match_baseline`, `test_parameters_are_backward_compatible`, `test_descriptions_are_concise`, `test_annotations` (expect `readOnlyHint: true`) and `test_no_agent_id_parameter` to cover it (AC7) — no new test code needed beyond the fixture entry.
- **Pagination (modify), `tests/test_paging_offset.py`:** add `("itglue_list_account_users", "/users", {})` to the `LISTS` table (`:40-48`) — reuses the existing `test_cut_pages_walked_by_next_offset_return_every_record_once` test to cover AC4 with zero new test code.
- **Errors/credentials (inherited):** AC5 and AC6 are already covered generically by `test_missing_credentials_envelope` and `test_error_mapping` (`tests/test_handlers.py:41-65`), which exercise the shared `run()`/`ITGlueClient` path every tool goes through; no per-tool duplicate is needed, since nothing in the new tool changes that path.
- **No real IT Glue account needed** for any of the above — all tests mock the HTTP layer with `respx`, same as every existing test in this repo. The INT publish step re-runs this suite before deploying, which is the closest thing to an integration check this repo has.

### Effort & breakdown

Small, single sub-task: ~50-70 lines in the new `tools/users.py`, a 2-line `server.py` registration, a README table row + one behaviour note, one `tools_baseline.json` entry, one `LISTS` entry, and 2-3 new unit tests. Estimated 0.5 day including review.

### Risks & dependencies

- No dependency on another ticket, no gateway change, no migration.
- IT Glue's `filter[name]` on `/users` is exact-match only (per the public API docs), unlike the fuzzy-feeling name filters elsewhere in this connector (e.g. `search_organizations`, `search_locations` do not document this restriction). Documented as a README behaviour note, not a code risk, but worth calling out so the dev leg doesn't assume partial matching.
- No live IT Glue account is available to verify behaviour end-to-end before INT; the dev leg's self-test is limited to mocked-HTTP unit tests plus the INT publish's own deploy/health check (same limitation every other tool in this connector has had).

## Test cases

(the pass/fail statements live here; full steps in the sibling `.ac.json`)

- **TC-IGU-001 · AC1** — Given valid credentials and no filters, calling `itglue_list_account_users` returns the standard list envelope with each item carrying `id`, `first_name`, `last_name`, `email`, `role_name`, `my_glue`, `last_sign_in_at`.
- **TC-IGU-002 · AC2** — Given `name`, `email` and `role_name` are passed, they are forwarded as `filter[name]` / `filter[email]` / `filter[role_name]` on the upstream `GET /users` call.
- **TC-IGU-003 · AC3** — Given `sort="-last_sign_in_at"` is **not** a legal value per IT Glue's documented sort fields, and `sort="-created_at"` is, the `sort` parameter is forwarded unchanged to IT Glue (the server does not validate it locally, matching every other tool).
- **TC-IGU-004 · AC4** — Given more users than fit on one page, walking the result by `next_offset` returns every user exactly once, including across a page IT Glue cuts short.
- **TC-IGU-005 · AC5** — Given the `X-ITGlue-API-Key` header is absent, `itglue_list_account_users` returns `{"error": {"code": "not_configured", ...}}`, not an exception.
- **TC-IGU-006 · AC6** — Given IT Glue returns 429 then 200, `itglue_list_account_users` retries once (honouring `Retry-After`) and returns the successful envelope; given IT Glue returns 403, it returns `{"error": {"code": "unauthorized", "retryable": false}}`.
- **TC-IGU-007 · AC7** — Given `tools/list` is queried, `itglue_list_account_users` is present with `readOnlyHint: true`, no `agent_id` parameter, and every previously-registered tool is still present with its previous parameters.
