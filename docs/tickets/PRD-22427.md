# PRD-22427 · [Feature] IT Glue password folder support

## Requirement understanding

One line: Let the IT Glue connector choose a password folder: a new tool that lists an organization's password folders, plus an optional folder ID on create_password, update_password and search_passwords, so Forte Technologies' onboarding agent can put each new user's password entry into the "MSPbots" folder without a technician moving it by hand.

The reporter (Don Gonzales, for Forte Technologies / Contemporary Staffing Solutions) confirmed this is a Feature, not a Bug: the connector never had a folder option. Today `create_password` takes only organization, name, password, username, url, notes and category, so every entry lands at the organization's top level and a technician moves it manually (`src/itglue_mcp/tools/passwords.py:117-139`). There is also no way to find a folder ID by name. The first useful slice is "look up the folder, create the entry inside it"; moving entries and searching by folder are the rest of the request. Intake comment #1600390000136001 states the Done when (DW1..DW5, tested on a test IT Glue organization, not on Forte's live data) and says "No AP-UX verification for MCP cards".

## Product design

### Goals / Non-goals

Goals (what an agent or technician using the IT Glue connector can observe):

- G1. An agent can list the password folders of one IT Glue organization (id, name, parent folder id) and find a folder, e.g. "MSPbots", by name.
- G2. `create_password` can place the new entry inside a chosen folder.
- G3. `update_password` can move an existing entry into a chosen folder.
- G4. `search_passwords` can be limited to one folder.
- G5. Calls that do not pass a folder ID behave exactly as today (entry at the organization's top level, no filter).

Non-goals (not in Done when, not built):

- Creating, renaming, deleting or restricting password folders.
- Moving an entry back to the top level (clearing the folder).
- Listing the entries of nested sub-folders recursively.
- Any change to Forte's own IT Glue data, the onboarding agent, or other connectors. Moving the already-created entries is not part of this ticket.

### Acceptance criteria AC1..ACn

- AC1 (DW1). Given an organization that has password folders, when the folder-list tool is called with that organization ID, then it returns each folder with its id, name and parent folder id (empty for a top-level folder), paged like the other list tools; given a name, only folders whose name contains it (case-insensitive) are returned.
- AC2 (DW2). Given a folder ID in the same organization, when `create_password` is called with it, then the new entry is created inside that folder (it shows that folder when read back or viewed in IT Glue) and the secret is not echoed.
- AC3 (DW3). Given an existing entry and a folder ID, when `update_password` is called with only that folder ID, then the entry is moved into the folder and its other fields are unchanged.
- AC4 (DW4). Given the entry from AC2, when `search_passwords` is called with the folder ID, then the entry is returned and entries outside the folder are not.
- AC5 (DW5). Given calls to `create_password`, `update_password` and `search_passwords` that do not pass a folder ID, then they behave as before: the new entry is at the organization's top level, an update without folder changes only the passed fields, and a search sends no folder filter.
- AC6 (error handling, same conduct as every tool in the connector). Given a non-numeric folder or organization ID, then the call returns `{"error": {"code": "invalid_argument"}}` without calling IT Glue; given a folder ID IT Glue rejects, then IT Glue's error is returned in the standard envelope, never raised.

### Open questions

- Q1 (does not block implementation). Whether IT Glue accepts `password-folder-id` on create and update is reporter-supplied, unverified. Assumption carried: it is accepted on update; on create it may be ignored. The design makes the tool correct either way (create-then-move fallback, see Tech design). If IT Glue accepts neither on create nor update, the ticket cannot be delivered as specified and the developer must return it with the observed API response.
- Q2 (does not block). Clearing a folder (moving back to the organization's top level) is not requested; not built. Assumption: not needed for Forte's onboarding use.
- Q3 (does not block). Name lookup is a local match on the returned page, as `list_document_folders` does; organizations with more than one page of folders are walked with `offset`. Assumption: an organization has few folders, so this is acceptable.

## Tech design

### Conclusion

One new read tool `list_password_folders`, and one optional parameter `password_folder_id` on each of `create_password`, `update_password`, `search_passwords`, all in `src/itglue_mcp/tools/passwords.py`. No new module, no new dependency, no required parameter added. `create_password` sends the folder as an attribute and, if IT Glue's response does not show that folder, moves the entry with one follow-up PATCH, so the result is correct whether or not IT Glue honours the attribute on create. Delivery = code + tests + README row + baseline + a `docs/changes/` entry. Story points: 2.

### Where the current implementation lives

- `src/itglue_mcp/tools/passwords.py:39-181`: the whole Passwords area, registered once in `register(mcp, settings)` (`src/itglue_mcp/server.py:58`).
- `src/itglue_mcp/tools/_common.py`: `READ`/`CREATE`/`UPDATE` annotations (`:22-24`), `locate()` paging (`:47-55`), `run()` envelope and secret masking (`:80-106`), `seg()` numeric ID guard.
- `src/itglue_mcp/api.py`: `page()` (`:191`), `keep_matching()` (`:231`), `attributes()` (`:241`, dasherizes keys and drops `None`), `item()` (`:176`).
- Pattern to copy: `list_document_folders` (`documents.py:180-206`) and the folder attribute on `create_document` (`documents.py:224-234`).

### Option analysis

- A (chosen): add the folder ID as an optional attribute/filter next to `password_category_id`, add a folder-list tool shaped like `list_document_folders`. Smallest change, same shape as the existing tools, no breaking change.
- B: a separate "move_password" tool. Rejected: the ticket asks `update_password` to move, and a second write tool for one attribute adds surface for no gain.
- C: resolve the folder by name inside `create_password` (`password_folder_name`). Rejected: hides an extra read call and an ambiguity rule (several folders with the same name, nested folders) inside a write; the ticket explicitly wants lookup then ID.
- D: always create at top level then PATCH. Rejected as the only path: costs two calls on every create and leaves a top-level entry on partial failure. Kept only as the fallback when the response does not show the folder.

### Data & API contract

New tool `list_password_folders`:

```
Request:  {"organization_id": 123, "name": "MSPbots"}
Upstream: GET /organizations/123/relationships/password_folders?page[size]=50&page[number]=1
Response: {"items": [{"id": "77", "name": "MSPbots", "parent_id": null, ...}],
           "count": 1, "page_number": 1, "page_size": 50, "has_more": false, "offset": 0}
```

Attributes are passed through as IT Glue returns them (flattened, snake_case by `api.flatten`). The parent-folder attribute is expected to be `parent_id` in IT Glue's folder resource; this is reporter/public-doc based and unverified, so the tool does not rename or interpret it. Documentation of the tool says "parent folder (empty for top level)".

`create_password`:

```
Request:  {"organization_id": 123, "name": "Jane Doe - Microsoft 365", "password": "***", "password_folder_id": 77}
Upstream: POST /organizations/123/relationships/passwords
          {"data": {"type": "passwords", "attributes": {"name": "...", "password": "***", "password-folder-id": 77}}}
Fallback: if response attributes["password-folder-id"] != 77 -> PATCH /passwords/<id>
          {"data": {"type": "passwords", "attributes": {"password-folder-id": 77}}}?show_password=false
```

Without `password_folder_id` the body is byte-for-byte what it is today. `update_password`: same attribute in the existing PATCH body. `search_passwords`: `filter[password_folder_id]=77` in the existing GET. Errors keep the standard envelope. The secret is never in a response or log (secrets list passed to `run`).

Compatibility: all three parameters are new and optional; `tools_baseline.json` check still passes; existing callers are unaffected.

### Key flow / sequence

Onboarding agent: `search_organizations` -> `list_password_folders(organization_id, name="MSPbots")` -> `create_password(..., password_folder_id=<id>)` -> optional check `search_passwords(organization_id, password_folder_id=<id>)`.

### Non-functional

- Security: credentials still only from request headers; `password` stays marked secret in the schema and masked in errors; folder responses carry no secrets. IDs go through `seg()` so they cannot alter the URL path. IT Glue enforces folder/organization permissions and returns 403/404, mapped to the standard envelope; a folder from another organization is rejected by IT Glue, not by us.
- Idempotency and concurrency: create is not idempotent (unchanged; docs already say search first). The fallback PATCH is idempotent. Partial failure returns the entry with a warning instead of an error to avoid duplicate creates on retry.
- Performance: one extra GET for lookup; at most one extra PATCH on create when the API ignores the attribute. Retries and budget unchanged (`api.py:107-146`).
- Observability: existing request log and error envelope; no new log lines carry secrets.

### Rollout & rollback

Ships through the normal INT publish after review. Rollback is a revert of the merge: the change is additive and the new parameters are optional, so no data migration and no ordering with other repos. Release order: no dependency (single repo).

### Test strategy

Mocked HTTP with `respx` in `tests/test_passwords.py`, one behavior per test:

- folder list: params, items with id/name/parent, name filter, paging/offset, non-numeric organization ID, upstream 404.
- create with folder: attribute sent as `password-folder-id`; response shows folder -> exactly one upstream call; response does not show the folder -> one PATCH follows; PATCH fails -> entry returned with `warning`; secret absent from every output; create without folder -> body has no folder attribute.
- update with only folder: PATCH carries only the folder; update with nothing still returns the "Pass at least one field" error.
- search with folder: `filter[password_folder_id]` present; absent when not passed.
- baseline/compat: `tests/test_tools.py` with the updated baseline; `uv run ruff check . && uv run ruff format --check .`; `uv run pytest -q`.
- Manual / real account (not run by DEV01 unless a test IT Glue organization is available): the DW1..DW5 round trip on a test organization, including Q1 (does create accept the folder).

Regression surface: the three existing password tools and the tools baseline.

### Risks & dependencies

- R1 (medium): IT Glue may ignore the folder attribute on create, or on update too. Mitigation: response check plus fallback PATCH; if update also ignores it, the developer returns the ticket with the observed API response (Q1).
- R2 (low): parent attribute name in the folder resource differs from `parent_id`. Mitigation: pass-through, no mapping; tests use the documented shape.
- R3 (low): organizations with many folders need several pages to find a name. Mitigation: standard `offset` paging.
- Dependencies: none on other tickets or repos. Test data: a test IT Glue organization with a password folder and a real IT Glue API key, available to the testers on INT only; DEV01 may not have it.
