## Requirement understanding

One line: Add a tool to the IT Glue MCP connector that lists IT Glue contacts filtered by organization and email, so the Rewst flow that maps an M365 user to its IT Glue contact (it_glue.list_contacts) can be rebuilt as an MSPbots agent.

This ticket is item 62 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It targets the Rewst account "EMD Networking Services", whose "ITG: Get Contact Asset" sub-flow (365-day run evidence, level B) calls IT Glue's `it_glue.list_contacts` action with `filter.organization_id` and `filter.primary_email` to find the IT Glue contact that corresponds to a given Microsoft 365 mailbox. The gap is that the MSPbots IT Glue connector has no tool that reads contacts at all — not a parameter gap on an existing tool, a missing resource.

## Product design

### Goals / Non-goals

**Goals**

- Add one new read-only tool, `itglue_list_contacts`, that lists IT Glue contacts filtered primarily by organization and email (the ticket's own stated use case: mapping an M365 user to its IT Glue contact), with enough fields (name, email, organization) to identify the right contact, matching the capability the ticket asks for.
- Keep it filterable and sortable the same way every other list tool in this connector is (paging via `page_size`/`page_number`/`offset`, `sort`), so agents that already know this connector's conventions can use it without new concepts.

**Non-goals**

- No write operations on contacts (create/update/archive/delete) — the ticket and the Rewst flow it replaces are both read-only (a lookup step inside a documentation sub-flow).
- No `get_contact` (single-contact-by-id) tool — the ticket's Rewst flow only ever looks a contact up by organization + email, i.e. only ever needs the list endpoint; a get-by-id tool is a plausible follow-up but is not asked for here (YAGNI).
- No change to any existing tool's name, parameters, or behaviour.
- No UI change — this is a connector-level (MCP) change, not an Agent Platform page.
- No new connector and no gateway change — the repo already exists and this is an in-repo addition, same shape as PRD-21586 (`itglue_list_account_users`) and PRD-21217 (flexible asset management) before it.

### Acceptance criteria AC1..ACn

- **AC1** — Given valid IT Glue credentials and no filters, when `itglue_list_contacts` is called, then it returns the connector's standard list envelope (`items`, `count`, `page_number`, `page_size`, `has_more`[, `total_count`, `offset`, `next_offset`]) where each item carries at least `id`, `first_name`, `last_name`, `email`, `organization_id` and `title`.
- **AC2** — Given `organization_id` and/or `email` are passed (the ticket's own primary use case — mapping an M365 user's mailbox to its IT Glue contact within one client), when `itglue_list_contacts` is called, then they are forwarded as IT Glue's `filter[organization_id]` / `filter[email]`.
- **AC3** — Given `name`, `first_name`, `last_name` and/or `contact_type_id` are passed, when `itglue_list_contacts` is called, then each is forwarded as the matching `filter[...]` (`filter[name]`, `filter[first_name]`, `filter[last_name]`, `filter[contact_type_id]`), the same additive-filter pattern every other search tool in this connector uses.
- **AC4** — Given a `sort` value, when `itglue_list_contacts` is called, then the `sort` query parameter is forwarded unchanged (no local validation), matching every other list tool's sort parameter.
- **AC5** — Given the organization has more contacts than fit on one page, when a caller walks the result with `next_offset` (or `page_number`), then every contact is returned exactly once, none are skipped or duplicated, and a cut page continues exactly where the previous one stopped — the same guarantee already enforced for every other list tool.
- **AC6** — Given missing or invalid IT Glue credentials, when `itglue_list_contacts` is called, then it returns the same structured error envelope as every other tool (`not_configured` when the header is absent, `invalid_argument` when the region/base URL header is malformed) — never an unhandled exception.
- **AC7** — Given IT Glue returns an error (401/403, 404, 422, 429, or 5xx), when `itglue_list_contacts` is called, then the error is mapped through the existing `code` / `message` / `retryable` envelope exactly as it is for every other tool, with the retryable ones retried with backoff.
- **AC8** — Given the MCP's `tools/list` is queried, when `itglue_list_contacts` is registered, then it is read-only (`readOnlyHint: true`), has no `agent_id` parameter, is listed in `README.md`'s Tools table, and does not remove or change any existing tool's name or parameters.

### Open questions

- **Field/filter name mismatch between the ticket and the vendor's public docs — not blocking.** The ticket asks for `filter.primary_email` and `filter.psa_id`, and a response field `contact-emails[]`; the two independent reads of IT Glue's public API docs described above show `filter[email]` (not `primary_email`), no `psa_id` filter on this endpoint, and a singular `email` attribute (not a plural `contact-emails` array). Proceeding on the same assumption PRD-21586 made for an analogous mismatch (`first-name`/`last-name` vs. a requested combined `name`): expose IT Glue's actual attributes and filters as the connector's own `api.flatten()` returns them, rather than inventing fields IT Glue does not document — consistent with how every other tool in this connector works. `organization_id`, `first_name`, `last_name`, `contact_type_id` and `sort` are included as filters because the public docs and the ticket agree on them; `email` is included under that name (not `primary_email`) because that is what the docs show and no tool in this connector renames a filter to match a requester's wording. `psa_id` is **not** added as a filter — it is not documented for this endpoint (unlike `search_organizations`, which does document `filter[psa_id]`) and forwarding an unsupported filter key would silently do nothing; if a real IT Glue account later shows `psa_id` does work on `/contacts`, that is a one-line follow-up, not a reason to hold this ticket. If the ticket's author specifically needs a `psa_id` filter or a combined `contact-emails` field once this ships against a live account, say so in a comment and move the ticket back to `5b - ready for groom`.
- **No live IT Glue test account is available to DEV01.** Per `references/mcp-track.md` §3 ("completion standard"), missing a vendor test account does not block design or development; cases that need one are marked accordingly in the test cases below.
- **The vendor docs page itself was inconsistently fetched** (a large single-page doc; different fetch attempts returned different truncated slices). Two independent fetches agreed with each other on the Contacts filter/attribute list used above, which is the best available evidence without a live account to probe; not treated as blocking since the design uses the connector's existing "forward whatever filter the caller passes, do not validate locally" convention, so an unlisted-but-real filter would still work if IT Glue accepts it, and a listed-but-wrong one would simply return no matches rather than error.

## Tech design

### Conclusion

Add one new read-only tool, `itglue_list_contacts`, in a new module `src/itglue_mcp/tools/contacts.py`, registered in `src/itglue_mcp/server.py` next to the existing tool modules. It is a thin, filterable, paginated wrapper around `GET /contacts`, built entirely from the helpers every other list tool already uses (`api.page`, `api.flatten`, `tools/_common.py`'s `run`/`locate`/`READ`). No architectural change, no new dependency, no change to any existing tool. Same shape as PRD-21586's `itglue_list_account_users`.

### Option analysis

- **Chosen — new module `tools/contacts.py`, same shape as `organizations.py` and `users.py`.** One file, one tool, reuses every existing helper. Matches the repo's own convention of "one module per resource area" (`README.md:172`).
- **Rejected — add it to `tools/organizations.py`.** Contacts are a distinct IT Glue resource with their own endpoint and attribute set; organizations.py's docstring ("Organizations (MSP clients) and the connectivity check") is already about a different resource, and every other resource in this connector gets its own module even when closely related to another (e.g. `documents.py` vs. the separate document-sections tools within it, which at least share one endpoint family — contacts and organizations do not even share that).
- **Rejected — a generic "list any IT Glue resource" tool.** Over-generalizes for one new capability (YAGNI); every other tool in this connector has an explicit name and schema so the agent-facing contract stays discoverable and typed, same rejection reasoning as PRD-21586.
- **Rejected — adding a `get_contact(id)` tool in the same change.** Not asked for by the ticket or needed by the Rewst flow it replaces (that flow only ever searches by organization + email, never already has a contact id to look up); adding it now would be speculative scope, not a decision this design needs to make. Left as a natural, obvious follow-up if a future ticket needs it (see Non-goals).

### Data & API contract

Request (MCP tool call):

```
itglue_list_contacts(
  organization_id?: string, // forwarded as filter[organization_id] — the ticket's primary use case
  email?: string,           // forwarded as filter[email] (see Open questions: ticket says "primary_email")
  name?: string,             // forwarded as filter[name]
  first_name?: string,      // forwarded as filter[first_name]
  last_name?: string,       // forwarded as filter[last_name]
  contact_type_id?: string, // forwarded as filter[contact_type_id]
  sort?: string,             // one of name|id|created_at|updated_at, "-" prefix = descending (forwarded unvalidated)
  page_size?: int,          // default 50, max 200
  page_number?: int,        // default 1
  offset?: int               // overrides page_number; pass next_offset from a previous call
) -> string (JSON)
```

Upstream call: `GET /contacts` with `filter[organization_id]`, `filter[email]`, `filter[name]`, `filter[first_name]`, `filter[last_name]`, `filter[contact_type_id]`, `sort`, `page[size]`, `page[number]` — unset filters are omitted, same as every other tool (`src/itglue_mcp/api.py:117`).

### Key flow / sequence

1. Agent Platform / gateway calls `itglue_list_contacts` over MCP with the tenant's `X-ITGlue-API-Key` (+ optional region/base URL) headers, unchanged from every other call to this server.
2. `CredentialMiddleware` extracts and validates the headers (unchanged).
3. The new tool handler builds `filter[...]`/`sort` query params via the shared `locate()` helper and calls `GET /contacts` through the per-request `ITGlueClient`.
4. `api.page()` flattens the JSON:API response into the standard list envelope.
5. `run()` wraps any upstream error into the standard error envelope; nothing here is new.

Typical caller flow (matching the ticket's own Rewst use case): call `itglue_list_contacts(organization_id=<id>, email=<m365 mailbox>)` to find the single matching IT Glue contact for a given M365 user within a given client organization.

### Non-functional

- **Security:** no change to the credential model — API key stays header-only, never persisted, never logged (`src/itglue_mcp/tools/_common.py:80-106`). The `/contacts` resource has no secret fields, so no `drop` set is needed; see the Reuse & cleanup decision above. Contact records can carry personal data (name, email, phone); this is no different in kind from what `search_organizations`/`itglue_list_account_users` already expose and is gated by the same per-tenant API key.
- **Multi-tenant isolation:** unaffected. One `ITGlueClient` is created per request, scoped to that request's own API key (`src/itglue_mcp/api.py:92-99`); a tenant can only ever see the contacts of the IT Glue account its own key belongs to. No new state is introduced that could leak across tenants or requests.
- **Performance:** same `page_size` default (50) and cap (200) as every other list tool; this is a thin passthrough bounded by the existing retry/backoff logic in `api.py:107-146` (3000 requests / 5 minutes IT Glue rate limit, already handled generically).
- **Observability:** errors flow through the same `log.exception` / structured-envelope path as every other tool (`src/itglue_mcp/tools/_common.py:99-106`); nothing new to add.

Purely additive tool — no feature flag needed; adding a tool cannot break an existing caller. Rollback is a revert of the merge commit followed by a re-publish — no data or schema to roll back (this repo is stateless).
